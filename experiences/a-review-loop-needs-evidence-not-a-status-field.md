# حلقهٔ بازبینی به مدرک نیاز دارد، نه به یک فیلدِ وضعیت

## 🎯 چالش / Challenge

یک حلقهٔ بازخورد بین انسان و یک عاملِ خودکار: کاربر ایرادی را می‌بیند و ثبت
می‌کند، عامل می‌رود کار را انجام می‌دهد و نتیجه را زیرش می‌نویسد، کاربر تأیید
می‌کند، و مورد بایگانی می‌شود.

طراحیِ بدیهی یک فیلدِ `status` است: `open → answered → approved → filed`.

**و همین یک فیلد، حلقه را از بین می‌برد.** چون «جواب دادم» و «درستش کردم» هر دو
`answered` می‌شوند و هر دو یک رنگ می‌گیرند. عامل زیرِ پانزده مورد می‌نویسد «نشد»،
«بعداً»، «منتظرِ نظرِ شما» — و کاربر از دور یک دیوارِ سبز می‌بیند که می‌گوید همه
انجام شده. یک بار که کاربر این را بفهمد، **به کلِ سامانه بی‌اعتماد می‌شود** و
دیگر نگاهش نمی‌کند؛ از آن لحظه حلقه فقط هزینه است.

## 💡 راه‌حل / Solution

**دو محورِ جدا، و رنگ از محورِ دوم می‌آید:**

| محور | یعنی چه | چه کسی می‌نویسد |
|---|---|---|
| `status` | **کجای گفت‌وگو** هستیم | سیستم |
| `outcome` | **واقعاً چه شد** | فقط عامل |

`outcome` عمداً هیچ مقداری به معنای «فکر کنم درست شد» ندارد:
`fixed` · `partial` · `needs-owner` · `not-done`.

و سه نگهبان که ادعا را به مدرک گره می‌زنند:

1. **`fixed` بدونِ تصویرِ بعدش رد می‌شود** (هم در API، هم در ابزارِ عامل).
   اگر نمی‌توانی نتیجه را نشان بدهی، `not-done` بنویس.
2. **رنگ مشتق است، نه ذخیره‌شده.** یک تابعِ خالص از `status` + آخرین یادداشتِ
   عامل. ادعای «انجام شد» بدونِ عکس، **زرد** نشان داده می‌شود نه سبز.
3. **تأیید فقط دستِ کاربر است — و این یک گاردِ اجرایی است، نه یک قاعدهٔ نوشته‌شده.**
   حسابِ عامل از endpointِ تأیید رد می‌شود.

## 🧪 نمونه کد (Anonymized)

```python
def glow(status, notes):
    """رنگی که کاربر از دور می‌بیند — مشتق، نه ذخیره‌شده."""
    if status == APPROVED: return APPROVED          # تیکِ خودِ کاربر بر همه مقدم است
    if status in (FILED, OPEN): return status
    last = next((n for n in reversed(notes) if n["by"] == "agent"), None)
    outcome = (last or {}).get("outcome")
    if not outcome:
        return STALE                                 # جوابِ قدیمی؛ مدرکِ اصلاح نیست
    if outcome == FIXED and not last.get("after_shot_id"):
        return PARTIAL                               # ادعا بدونِ مدرک ⇒ سبز نمی‌شود
    return outcome
```

## ⚠️ نکات حیاتی / Pitfalls

- **«عامل کیست؟» باید روی سرور تعریف شود، نه در محیطِ اجرای عامل.** اگر گارد
  فقط یک متغیرِ محیطی را بخواند که در ماشینِ عامل است، سروری که آن را نمی‌شناسد
  عامل را کاربرِ عادی می‌بیند: برای ثبتِ نتیجه fail-closed (خوب) ولی برای
  **تأیید fail-open** (بد). این را تستِ انتها-به-انتها پیدا کرد، نه بازبینیِ کد.
- **نشانی ذخیره کن، نه مختصات.** موقعیتِ پیکسلی با اندازهٔ پنجره عوض می‌شود.
  چیزی که به درد می‌خورد **راهِ بازگشت** است: کدام صفحه، کدام بخش، و یک رشته که
  همان‌جا را باز می‌کند. یک ویژگی روی لایهٔ اصلیِ چیدمان، همهٔ صفحه‌ها را
  گزارش‌پذیر می‌کند.
- **دربارهٔ تصویر صادق باش.** مرورگر نمی‌تواند از DOMِ خودش عکس بگیرد؛ رستریزر
  یک **بازسازی** است. اگر آن را «این چیزی است که دیدم» جا بزنی، بدتر از نداشتنش
  است. یا صریح بگو بازسازی است، یا از کاربر بخواه اسکرین‌شاتِ واقعیِ خودش را
  بچسباند (Ctrl+V) — که مدرکِ بهتری هم هست.
- **صفِ بی‌جواب باید اجرا را قرمز کند.** ابزارِ کشیدنِ صف با کدِ غیرصفر خارج
  شود تا دوری که صف را نادیده گرفته شبیهِ دورِ سالم نباشد.
- **یادداشتِ تازهٔ کاربر روی یک موردِ پاسخ‌داده‌شده باید آن را دوباره باز کند**،
  وگرنه «یک چیزِ دیگر هم هست» در حالتِ `answered` دفن می‌شود.

## 🔁 چطور در جای دیگر اعمال کنیم / How to Apply Elsewhere

برای هر حلقهٔ «گزارش → اقدام → تأیید»:

1. آیا «پاسخ داده شد» از «انجام شد» قابلِ تفکیک است؟ اگر نه، اولین کار همین است.
2. ادعای موفقیت به چه **مدرکی** گره خورده؟ اگر به هیچ، یعنی به حرف.
3. رنگ/نشانگرِ خلاصه از کدام فیلد می‌آید؟ باید از نتیجه بیاید، نه از وضعیت.
4. تأیید را چه کسی می‌تواند بزند — و آیا این یک **گارد** است یا فقط یک جمله در مستندات؟
5. اگر عامل صف را نادیده بگیرد، کسی می‌فهمد؟
6. نشانیِ ثبت‌شده بعد از تغییرِ اندازهٔ پنجره هنوز معتبر است؟
