# کنترلی که وضعیت را می‌سازد، نباید پشتِ همان وضعیت پنهان شود

## 🎯 چالش / Challenge

یک فرم، فیلدی دارد که «آیا این سند ضمیمه دارد؟» را اعلام می‌کند
(`hasEnclosure: yes/no`). دکمه‌ای هم هست که ضمیمه را **می‌سازد** (آپلود
می‌کند). برای «تمیزتر شدن UI»، دکمه پشتِ همان فیلد گیت شد:

```tsx
{hasEnclosure && <button onClick={openPanel}>افزودن ضمیمه</button>}
```

نتیجه یک **بن‌بستِ منطقی** شد: هر سندی که با `no` ذخیره شده بود، دکمه‌اش
ناپدید می‌شد. کاربر که نمی‌داند ناپدید‌شدن به آن select مربوط است، فقط
می‌بیند «دکمه بین بقیهٔ دکمه‌ها بود، حالا نیست» و گمان می‌کند یک قابلیت
حذف شده. بدتر: build سبز است، تست‌ها سبزند، و هیچ خطایی در کنسول نیست.

الگوی کلی: **کنترل A وضعیت S را تولید می‌کند، ولی نمایشِ A مشروط به S است.**
تا وقتی S خودش دستی روشن نشود، A غیرقابل‌دسترس است — و چیزی به کاربر
نمی‌گوید کدام سوییچ را باید بزند.

## 💡 راه‌حل / Solution

جهتِ وابستگی را **برعکس** کن: به‌جای اینکه پرچم، کنترل را گیت کند، پرچم
از واقعیت **پیروی** کند.

1. کنترلِ سازنده را **همیشه** رندر کن — بی‌قید و شرط.
2. وقتی چیز واقعی ساخته شد (فایل آپلود شد / آیتم اضافه شد)، پرچم را
   خودکار به «بله» ببر.
3. هرگز خودکار به «خیر» برنگرد — این تصمیمِ کاربر است.
4. اگر پرچم و واقعیت با هم نخوانند (سندِ قدیمی که ضمیمه دارد ولی
   پرچمش «خیر» است)، **بگو** و یک دکمهٔ اصلاحِ تک‌کلیکی بده — پنهان‌کردنِ
   کل پنل، «حل» نیست.
5. قرارداد را با یک تستِ source-level قفل کن، چون build این را نمی‌گیرد.

## 🧪 نمونه کد (Anonymized)

```tsx
// ❌ بن‌بست: کنترل پشتِ وضعیتی که خودش می‌سازد
{hasEnclosure && <button onClick={openPanel}>افزودن ضمیمه</button>}
{hasEnclosure && panelOpen && <EnclosurePanel />}

// ✅ پرچم از واقعیت پیروی می‌کند
const markHasEnclosure = () =>
  setForm((s) => (s.hasEnclosure === 'yes' ? s : { ...s, hasEnclosure: 'yes' }))

<button onClick={() => setPanelOpen((v) => !v)}>افزودن ضمیمه</button>
{panelOpen && (
  <EnclosurePanel
    onUploaded={markHasEnclosure}
    notice={!hasEnclosure && items.length > 0
      ? <Fix onClick={markHasEnclosure} />   // واقعیت و پرچم نمی‌خوانند
      : null}
  />
)}
```

تستِ قفل‌کنندهٔ قرارداد (روی متنِ سورس، نه رندر):

```ts
const SRC = readFileSync(join(__dirname, 'page.tsx'), 'utf8')
const i = SRC.indexOf('افزودن ضمیمه')
expect(SRC.slice(i - 500, i)).not.toContain('hasEnclosure &&')  // دوباره گیت نشود
expect(SRC).not.toContain("hasEnclosure: 'no'")                 // خودکار برنگردد
```

## ⚠️ نکات حیاتی / Pitfalls

- **«پنهان‌کردن» با «حذف‌نکردن» فرق ندارد** وقتی کاربر راهِ برگرداندنش را
  نمی‌داند. یک قابلیتِ نادیدنی، عملاً حذف‌شده است.
- **گیتِ رندر در git blame گم می‌شود.** دکمه در دیف حذف نشده، فقط یک
  `{flag && (` جلویش اضافه شده؛ `git log -S "<button…"` چیزی پیدا نمی‌کند.
  با `git log -S "<نامِ متغیرِ گیت>"` بگرد.
- **کلونِ shallow، تاریخچه را قطع می‌کند**: اگر کامیتِ معرفیِ گیت روی مرزِ
  graft باشد، کلِ فایل «افزوده‌شده» به نظر می‌رسد و نمی‌شود فهمید قبلش
  چه بوده. پیش از نتیجه‌گیریِ «همیشه همین بوده»، `.git/shallow` را چک کن.
- **گیتِ یکسان معمولاً چند جا تکرار شده** — دکمه، پنل، و ابزارهای وابسته.
  همه را با هم باز کن، وگرنه دکمه برمی‌گردد ولی پنل باز نمی‌شود.
- **پرچم را روی load دستکاری نکن.** اصلاحِ خودکارِ یک سندِ ذخیره‌شده در
  لحظهٔ باز شدن، تغییرِ بی‌اجازه است؛ پیشنهادِ اصلاح بده، اجرا نکن.

## 🔁 چطور در جای دیگر اعمال کنیم / How to Apply Elsewhere

برای هر `{flag && <Control/>}` در کد این چهار سؤال را بپرس:

1. آیا خودِ `Control` یکی از راه‌های تولیدِ `flag` است؟ اگر بله ⇒ **بن‌بست**،
   گیت را بردار.
2. اگر `flag` خاموش باشد، آیا چیزی روی صفحه هست که به کاربر بگوید چرا
   کنترل نیست و چطور روشنش کند؟ اگر نه ⇒ گیت را با یک «حالتِ غیرفعال +
   توضیح» عوض کن، نه پنهان‌سازی.
3. آیا `flag` می‌تواند با واقعیت واگرا شود (داده‌های قدیمی، ایمپورت،
   ویرایشِ دستی)؟ اگر بله ⇒ واگرایی را نشان بده و اصلاحِ تک‌کلیکی بده.
4. چه‌کسی `flag` را روشن می‌کند؟ اگر جواب «کاربر، از یک جای دیگرِ صفحه»
   است، آن وابستگی باید روی صفحه **دیده** شود.

چک‌لیستِ اجرا: گیت را بردار → مسیرهای واقعیِ ساخت را به setterِ پرچم وصل کن
→ برگشتِ خودکار را ممنوع کن → واگرایی را اعلام کن → تستِ source-level بنویس
→ در مرورگرِ واقعی، با پرچمِ **خاموش**، ببین کنترل هست.
