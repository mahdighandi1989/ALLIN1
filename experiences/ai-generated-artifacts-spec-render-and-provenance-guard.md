# AI-generated artifacts: strict spec → server render → provenance guard

## 🎯 چالش / Challenge

کاربر می‌خواهد AI برایش «فایل واقعی» بسازد (مثلاً جدول اکسل یا متن ورد از
داده‌های دیتابیس) و همان‌جا به‌عنوان پیوست ثبت شود. سه خطر:

1. اگر خودِ مدل فایل/باینری بسازد، خروجی غیرقابل‌اعتماد و غیرقابل‌ولیدیشن است.
2. مدل ممکن است دادهٔ گمشده را «اختراع» کند.
3. **چرخهٔ داده:** اگر همان سیستم یک ابزار «استخراج از پیوست‌ها → دیتابیس» هم
   داشته باشد، فایلِ ساختهٔ AI (که داده‌اش از خودِ DB آمده) دوباره وارد DB
   می‌شود — نویزِ تکراری با ظاهرِ «سند جدید».

## 💡 راه‌حل / Solution

1. **مدل فقط spec پیشنهاد می‌دهد، نه فایل:** خروجی مدل یک JSON با اسکیمای
   بسته (`kind`, `filename`, `title`, `warnings`, `sheets|paragraphs`).
2. **سرور مرجع است:** پارسر قطعی spec را ولیدیشن/کلمپ می‌کند (سقف شیت/سطر/
   ستون/طول سلول، sanitize نام فایل و نام شیت، None→خالی، مقادیر نامعتبر→
   پیش‌فرض امن، خروجی بی‌ساختار→reject) و خودش با کتابخانهٔ واقعی
   (openpyxl / python-docx) فایل را رندر می‌کند.
3. **قانون داده:** فقط از حقایقِ پاس‌داده‌شدهٔ DB + متنِ دستور؛ دادهٔ گمشده =
   سلول خالی + یک `warning` که در UI نمایش داده می‌شود — هرگز اختراع نشود.
4. **نشان منشأ (provenance):** فایل ذخیره‌شده با مارکر ثابت در metadata
   (مثلاً `notes` با پیشوند `AI_GENERATED:`) و لیستینگ API یک فلگ بولی
   (`ai_generated`) بدهد.
5. **گارد چرخه در مصرف‌کننده:** هر ابزار ingestion/استخراج، آیتم‌های
   `ai_generated` را **پیش‌فرض بی‌تیک** کند (انتخاب صریح کاربر همچنان مجاز)
   و دلیلش را همان‌جا در UI توضیح دهد.

## 🧪 نمونه کد (Anonymized)

```python
# server-side gate: model text → validated spec → real file
spec, warnings = parse_spec(model_text)      # clamps + sanitizes, raises on garbage
data, filename, mimetype = render(spec)      # openpyxl / python-docx
store(data, filename, notes=f"AI_GENERATED: {instruction[:400]}")
```

```ts
// consumer default-exclusion with explicit opt-in (tri-state via ??)
const selected = (a: Attachment) => picks[a.id] ?? !a.ai_generated
// "select all" must set every id EXPLICITLY true, otherwise {} re-excludes them
```

## ⚠️ نکات حیاتی / Pitfalls

- **`?? !flag` نه `!== false`:** اگر انتخاب پیش‌فرض با `map[id] !== false`
  پیاده شده باشد، «پیش‌فرضِ متفاوت برای گروهی از آیتم‌ها» ممکن نیست؛ به
  `map[id] ?? defaultFor(item)` مهاجرت کن و دکمهٔ «انتخاب همه» را صریح کن
  (`{}` دیگر به‌معنی «همه» نیست).
- **رندر RTL در docx:** جهتِ راست‌به‌چپ فقط در سطح پاراگراف (`w:bidi`)؛
  پرچم `rtl` روی runها یک override است و متن لاتین/عدد را آینه می‌کند.
- **sanitize نام فایل و نام شیت جدا هستند:** اکسل روی `[]:*?/\` در نام شیت
  خطا می‌دهد حتی اگر نام فایل تمیز باشد.
- **warnings را گم نکن:** تنها راهِ فهمیدن «چه چیزی در DB نبود» همین است؛
  در پاسخ endpoint و در UI پاس بده.
- مارکر منشأ را **پیشوندِ** فیلد متنی موجود کن (`startswith`)، نه substring —
  متن آزادِ کاربر می‌تواند اتفاقی شامل کلمه شود.

## 🔁 چطور در جای دیگر اعمال کنیم / How to Apply Elsewhere

- [ ] هر جا AI «فایل/آرتیفکت» تولید می‌کند: مدل spec بدهد، سرور رندر کند.
- [ ] اسکیمای spec را ببند و برای هر فیلد سقف/پیش‌فرض امن تعریف کن.
- [ ] قانونِ «دادهٔ گمشده = خالی + warning» را در system prompt و در پارسر
  هر دو enforce کن.
- [ ] خروجی را با همان مسیر ذخیره‌سازیِ آرتیفکت‌های دستی ثبت کن (نه مسیر موازی).
- [ ] فلگ منشأ را در storage و در API لیستینگ اضافه کن.
- [ ] تمام مصرف‌کننده‌های ingestion را پیدا کن و default-exclusion بگذار؛
  تست بنویس که «آیتم ساختهٔ AI پیش‌فرض بی‌تیک است ولی تیک دستی کار می‌کند».

## Update 2026-07-07 — گاردِ چرخه باید سمتِ سرور هم باشد

تیکِ پیش‌فرضِ فرانت‌اند فقط UI feedback است؛ اگر «سرور مرجع است»، ingestion
endpoint خودش باید آیتمِ دارای نشانِ منشأ را رد کند و override فقط با یک فلگ
صریح در بدنهٔ درخواست (`allow_ai_generated: true`) ممکن باشد که UI تنها هنگام
تیکِ عمدی کاربر می‌فرستد. خطای typed برگردان (`error: "ai_generated_artifact"`)
تا کلاینت پیامِ فهمیدنی نشان دهد، و هر دو مسیر (ردِ پیش‌فرض + عبور با override)
را تست کن.

## Update 2026-07-07 — دسترسیِ داده باید هم‌عرضِ دامنهٔ درخواست باشد (پروتکل need_data)

انضباطِ «دادهٔ گمشده = خالی + هشدار» یک حالتِ شکستِ بی‌صدا دارد: اگر scope دادهٔ
تزریقی از scope درخواست کوچک‌تر باشد (مثلاً حقایقِ «یک مشتری» ولی درخواستِ
«فهرستِ کلِ یک شعبه»)، مدل صادقانه جدولِ خالی می‌دهد و کاربر فکر می‌کند داده در
سیستم نیست. راه‌حل بدونِ بازکردنِ دسترسی مستقیم مدل به DB:

1. در پرامپت یک **کاتالوگ** بده: نامِ مجموعه‌های whitelisted + شرحِ فیلدها +
   مقادیرِ واقعیِ فیلترهای کلیدی (مثلاً distinct شعبه‌ها) — مدل خودش معادلِ
   بین‌زبانی (فارسی↔لاتین) را از فهرست برمی‌دارد؛ متن‌تطبیقیِ سمتِ سرور لازم نیست.
2. مدل به‌جای جوابِ خالی، `{"need_data": {datasets, filter}}` برمی‌گرداند؛ سرور
   کوئریِ **قطعی، whitelisted و سقف‌دار** را اجرا می‌کند و یک دورِ دوم spec نهایی
   ساخته می‌شود (فقط یک دور؛ تکرار ⇒ خطای typed).
3. فیلترِ بی‌تطبیق ⇒ فهرستِ کامل + ستونِ فیلتر + warning («خودت فیلتر کن») —
   هرگز نتیجهٔ خالیِ خاموش.
4. دورِ دوم سقفِ خروجیِ بزرگ‌تر می‌خواهد (ردیف‌ها در spec بازتولید می‌شوند).

در پرامپتِ سیستم صریح بنویس: «هرگز به‌جای درخواستِ داده، جدولِ خالی یا دادهٔ
ساختگی نده».

## Update 2026-07-16 — قالبِ کاربر را «متن کن و به همان pipeline تزریق کن» (v63)

وقتی کاربر باید فایلِ نمونه/قالب (هر فرمتی) بدهد تا خروجیِ ساخته‌شده دقیقاً
همان شکل شود، ارزان‌ترین و امن‌ترین راه: (۱) یک endpointِ سبکِ «فقط متن»
(multipart، بدونِ ذخیره) که با همان استخراج‌گرِ قطعی/رونویسیِ موجود فایل را
متن می‌کند؛ (۲) تزریقِ همان متن به پرامپتِ ژنراتورِ موجود به‌عنوانِ بخشِ
«قالبِ الزامی» با سه قاعدهٔ صریح: بازتولیدِ عینیِ ساختار، دادهٔ فقط-از-DB،
و «سطرهای نمونهٔ داخلِ قالب داده نیستند» (وگرنه مدل مثال‌ها را به‌عنوان
داده کپی می‌کند). این‌طوری مسیرِ رندر/اعتبارسنجی/ذخیرهٔ قبلی دست نمی‌خورد و
حالت‌های سه‌گانه (فقط شرح/فقط قالب/هردو) فقط با اختیاری‌کردنِ instruction +
گاردِ «حداقل یکی» ساخته می‌شوند. مثل همیشه: پیامِ «بدون شرح» را صریح در
پرامپت بنویس، نه رشتهٔ خالی — رشتهٔ خالی مدل را به حدس می‌اندازد.

## Update 2026-07-16 — «فایل‌های منبع» = داده، «قالب» = شکل (v65)

وقتی کاربر علاوه بر قالب، فایل‌هایی می‌دهد که «محتوایشان» باید خوراکِ ساختِ
پیوست شود (هر فرمت، هر تعداد، قابلِ افزودن در هر زمان)، همان الگوی v63 را
گسترش بده — نه مسیرِ جدید:

1. **همان endpointِ «فقط متن» را برای هر فایلِ منبع هم صدا بزن** (فرانت‌اند،
   ترتیبی، فایل‌به‌فایل — زیرِ سقفِ gateway می‌ماند و پیشرفتِ per-file نشان
   می‌دهد). فایلِ ناخوانا ⇒ کلِ عملیات با پیامِ روشن قطع شود، نه ادامهٔ خاموش
   با دادهٔ ناقص.
2. **در پرامپت دو بخشِ جدا با نقشِ صریح:** «فایل‌های منبعِ داده» (سقف‌دار:
   ۸ فایل × ۲۰هزار نویسه) قبل از بخشِ «قالبِ الزامی» + قاعدهٔ سیستمیِ صریح:
   قالب فقط «شکل» را تعیین می‌کند و فایل‌های منبع فقط «داده» می‌دهند؛
   تعارضِ منبع↔پایگاه‌داده ⇒ مقدارِ فایلِ منبع + اعلامِ مغایرت در warnings.
   بدونِ این تفکیکِ صریح، مدل سطرهای نمونهٔ قالب را داده می‌پندارد یا
   دادهٔ منبع را با شکلِ خودش می‌آورد.
3. **گاردِ ورودی را با واقعیتِ جدید هم‌راستا نگه دار:** حداقل «شرح یا قالب»
   الزامی ماند — فایلِ منبعِ تنها بدونِ هیچ‌کدام معنی ندارد (مدل نمی‌داند چه
   بسازد) و 422 با پیامِ فارسیِ روشن برمی‌گردد.

از داده (این‌جا: لاگ‌های audit/journal) هم دسترسی داشته باشد، دو اشتباهِ
رایج را نکن: (۱) مسیرِ جدید و جداگانه نساز — همهٔ سطح‌های AI این repo از
یک گلوگاهِ واحد (`_gather_facts` → `build_facts`) تغذیه می‌شوند؛ داده را
همان‌جا اضافه کن تا analyze/full_check/پرامپتِ درون‌متنی/ژنراتور یک‌جا
پوشش بگیرند. (۲) جدولِ رشد-بی‌نهایت را کامل به پرامپت نریز — برای facts
سقفِ کوچکِ per-account (۴۰ ردیفِ جدیدترین + برشِ detail) و برای نیازِ
سراسری datasetِ need_data با کوئریِ خودش-محدود (ORDER BY desc + LIMIT در
SQL «قبل از» فیلترِ پایتونی) + سقفِ استانداردِ ردیف با warning. و چون
کلیدهای جدیدِ facts خودگویا نیستند، یک جملهٔ توضیحی در سرصفحهٔ بخشِ
حقایقِ پرامپت بگذار («این کلیدها = لاگِ کارهای همین حساب») — وگرنه مدل
داده را دارد ولی نمی‌داند برای «از لاگ‌ها استخراج کن» باید سراغِ همین برود.

## Update 2026-07-16 — «نامحدود» یعنی اسکنِ نامحدود + برشِ اعلام‌شده، نه پرامپتِ نامحدود (v67)

وقتی مالک می‌گوید AI باید «نامحدود» در یک جدولِ رشدکننده جستجو کند، تفکیکِ
درست این است: (۱) «جستجو» واقعاً نامحدود — کوئری با فیلترهای SQL (ILIKE/
تاریخ/کلیدها) روی کلِ جدول، بدونِ پیش‌محدودیتِ newest-N؛ (۲) «ارسال به
پرامپت» سقف‌دار اما هرگز خاموش: شمارِ واقعیِ یافته‌ها (COUNT جدا) همیشه
کنارِ ردیف‌های بریده گزارش شود + پیامِ «فیلتر را تنگ‌تر کن» — مدل با یک
حلقهٔ need، عملاً به هر بُرشی می‌رسد. برای این «need» چرخِ نو نساز: همان
الگوی need_data (یک فرصت، دورِ دوم با نتایج، ممنوعیتِ تکرار) را برای
need_logs کپی کن و ورودیِ مدل را قبل از SQL از یک sanitize‌گرِ واحد
(کلیدِ سفید + برشِ طول + bound parameter) عبور بده که هر دو سطح (دستیار و
ژنراتور) از همان استفاده کنند.

## Update 2026-07-17 — LRM «ایزوله» نیست؛ برای مقدارِ LTR در سندِ RTL از LRE/PDF استفاده کن (v74)

اگر صفحهٔ وب مقداری را با dir="ltr" ایزوله می‌کند (شماره‌نامه، تاریخ،
داخلی)، در خروجیِ docx جفتِ LRM دورِ مقدار «همان» رفتار را نمی‌دهد: LRM
فقط دو لنگرِ خنثی است و قطعه‌های عددیِ جدا-با-فاصله (کلاسِ EN) داخلِ
پاراگرافِ bidi همچنان راست‌به‌چپ چیده می‌شوند ⇒ خروجی آینهٔ وب می‌شود.
معادلِ واقعیِ dir="ltr" در متنِ ساده، embeddingِ LRE…PDF (U+202A/202C)
است — در Word نامرئی است؛ LRI/PDI (U+2066/2069) را Word به‌شکلِ مربع
می‌کشد و rtlِ سطحِ run هم ترتیبِ تاریخ را برمی‌گرداند (درسِ v46). و برای
عیب‌یابیِ docx در محیطِ بدونِ Word اول سلامتِ خودِ مبدل را بسنج:
LibreOfficeِ headless بدونِ import-filter حتی فایلِ سالم را «could not be
loaded» می‌گوید — از این خطا نتیجهٔ «فایل خراب است» نگیر.

## Update 2026-07-17 (تکمیل v74) — Word نه embedding را می‌فهمد نه w:rtl=false؛ LRM لای جداکننده‌ها (v77)

ادامهٔ درسِ v74 با شواهدِ فایلِ واقعیِ مالک (شناسنامه‌دار): موتورِ bidi
خودِ Word برای ترتیبِ قطعه‌های عددیِ جدا-با-فاصله، «هم» LRE/PDF و «هم»
پرچمِ w:rtl=false روی run را نادیده می‌گیرد. تنها چیزی که همهٔ موتورها
(قدیم و جدید) به آن عمل می‌کنند نویسهٔ عادیِ قویِ چپ یعنی LRM است — نه
در دو سرِ مقدار (بی‌اثر برای ترتیبِ داخلی)، بلکه «دو طرفِ هر جداکننده»:
هر اسلش/فاصله/خطِ تیره بینِ دو strong-L بیفتد تا N1 کلِ دنباله را LTR
قفل کند. و درسِ فرایندی: نسخهٔ build را داخلِ خودِ artefact حک کن
(docProps) — بدونِ آن، «فایل از کدام دیپلوی بود؟» هر چرخهٔ fix/test را
کور می‌کند.

## Update 2026-07-17 (تکمیل v77) — حضورِ عنصرِ w:rtl سمّی است؛ فقط-LRM نجات‌بخش است (v78)

فایلِ شناسنامه‌دارِ reflow-v77ِ مالک هنوز آینه بود — با اینکه LRMها
داخلِ مقدار حاضر بودند. تشریحِ XML مقصر را نشان داد: از v75 عنصرِ
`<w:rtl w:val="false"/>` روی runِ مقدار مانده بود و Word «حضورِ» این
عنصر را rtl-روشن می‌خوانَد (قرینهٔ درسِ v46 که rightToLeft:true تاریخ را
برمی‌گرداند) و بر LRMها غلبه می‌کند. ضمناً LRE (U+202A) در فونتِ
fallbackِ Word به‌شکلِ «|»ِ مرئی رسم می‌شود و runِ مقدارِ خالی
(فقط کنترل‌ها: U+202A/LRM/LRM/U+202C) کنارِ «اقدام‌کننده» زباله می‌کاشت.
درسِ نهاییِ کلِ زنجیرهٔ v74→v78: برای مقدارِ LTR داخلِ پاراگرافِ RTL در
docx **هیچ** عنصرِ w:rtl نگذار (نه true نه false)، **هیچ** کنترلِ
embedding نگذار (LRE/PDF/LRI/PDI)، فقط LRM دو طرفِ هر جداکنندهٔ
غیررقمی — و مقدارِ خالی را اصلاً run نکن.

## Update 2026-07-17 (پایانِ زنجیره) — jc در پاراگرافِ bidi منطقی است؛ مقدارِ عددی را با پایهٔ LTR بنویس (v79)

دو درسِ بستهٔ نهایی: (۱) در docx، داخلِ پاراگرافِ `w:bidi` مقدارِ
`w:jc="right"` یعنی «انتهای خطِ RTL» = چپِ بصری — Word تمامِ ترازها را
قرینه می‌کند. برای راستِ بصری jc را **حذف** کن (پیش‌فرضِ bidi = start =
راست در همهٔ موتورها) و برای چپِ بصری jc="right" بده. ما ۳۴ نسخه این را
literal فرض کرده بودیم و کلِ هدر قرینه می‌شد؛ علامتِ تشخیص: XML درست
به‌نظر می‌رسد ولی رندر همه‌چیز را سمتِ مخالف می‌نشاند. (۲) برای خطی که
جوهرش یک مقدارِ عددیِ LTR است (شماره‌نامه، تاریخ)، به‌جای جنگیدن با
موتورِ bidi داخلِ پاراگرافِ RTL، کلِ خط را پاراگرافِ **غیرِ bidi** کن با
ترتیبِ منطقیِ [مقدار][« : »][برچسب]: با پایهٔ LTR بازچینشِ قطعه‌های
عددی ناممکن است، برچسبِ فارسیِ انتهایی خودش درست RTL رندر می‌شود، jc هم
literal می‌شود — بدونِ هیچ LRM/embedding. این ترکیب در هر موتوری
(Word قدیم/جدید، LibreOffice، مرورگر) یک جور در می‌آید.

## Update 2026-07-17 (v80) — نمایشِ درست کافی نیست؛ ساختارِ runها باید بومیِ Word باشد

درسِ تکمیلیِ زنجیره: فایلی که «درست دیده می‌شود» ممکن است موقعِ

سه شرط دارد: (۱) برچسب و مقدار در دو runِ جدا؛ (۲) runهای صرفاً-فارسی
`<w:rtl/>` داشته باشند (بدونِ val، فقط حضور = true) — این همان چیزی است
که Word موقعِ تایپِ فارسی خودش می‌نویسد و بدونش درج در مرزِ دونقطه سمتِ
غلط می‌نشیند؛ (۳) rtl هرگز روی runِ رقم‌دار نرود (v46: ترتیبِ گروه‌های
رقم برمی‌گردد) و هرگز به‌صورتِ val="false" نیاید (v78: حضور = روشن).

و عرضِ ستون‌ها را از «عرضِ خودِ باکسِ» صفحه بگیر، نه لبه‌منهای‌حاشیه —

## Update 2026-07-17 (v81) — قلمروِ w:rtl: فقط داخلِ پاراگرافِ bidi

اصلاحِ درسِ v80: قاعدهٔ «runِ صرفاً-فارسی ⇒ `<w:rtl/>`» فقط داخلِ
پاراگراف‌های `w:bidi` درست است. داخلِ پاراگرافِ LTR-پایه (ترفندِ v79

پاراگرافِ bidi ⇒ runهای فارسی علامت‌دار (تایپِ بومی)؛ پاراگرافِ LTR-پایه
⇒ هیچ runی علامت نگیرد (نمایش را UBA با پایهٔ LTR تضمین می‌کند و تایپِ
رقم هم ذاتاً درست است).

## Update 2026-07-17 (v82) — به پیش‌فرضِ jc تکیه نکن؛ مقدارِ منطقی را همیشه صریح بنویس

تکملهٔ v79: «حذفِ jc برای راستِ بصری» فقط در سطحِ بدنه جواب داد؛ داخلِ
سلولِ جدول، Word همان پاراگرافِ bidi بدونِ jc را چپ‌چین رندر کرد
(پیش‌فرضِ سلول ≠ پیش‌فرضِ بدنه). قاعدهٔ پایدار: در پاراگرافِ bidi مقدارِ
jc را همیشه صریح و «منطقی» بده — راستِ بصری ⇒ jc="left" (start)، چپِ
بصری ⇒ jc="right" (end) — تا رفتار در بدنه و سلول یکسان شود.

## Update 2026-07-17 (v83) — چیدمانِ کنارهم در docx: قابِ w:framePr، نه جدول

وقتی دو بلوک باید کنارِ هم بنشینند (بلوکِ شماره/تاریخ در چپ، گیرنده در
راست)، جدولِ نامرئی راهِ غلطی است: (۱) کاربر در Word آن را به‌شکلِ
باکس/جدول می‌بیند و انتظارِ متنِ آزاد دارد؛ (۲) ترازِ پاراگراف داخلِ
سلول در Word قواعدِ پیش‌فرض/تفسیرِ خودش را دارد و حتی jc صریحِ منطقی هم
آن‌طور که در بدنه عمل می‌کند عمل نکرد. راهِ درست، تکنیکِ کلاسیکِ
سربرگ‌های Word است: `w:framePr` با لنگرِ صفحه — پاراگراف‌های متوالی با
framePr یکسان یک قابِ واحد می‌شوند، محتوایش متنِ عادیِ قابلِ‌ویرایش است،
مختصات/عرضش را می‌شود از چیدمانِ وب برداشت و متنِ آزاد دورش می‌پیچد.
و برای خطوطِ تزئینی (خط‌چینِ زیرِ موضوع) پاراگراف-بوردر نده — در Word
قابلِ دستکاری نیست؛ متنِ واقعیِ «-» بده تا کاربر کوتاه/بلند/حذفش کند.
