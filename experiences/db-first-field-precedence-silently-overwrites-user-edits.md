# DB-first precedence on a user-editable text field = silent data loss

## 🎯 چالش / Challenge

کاربر متنِ «وثایق و مدارک» نامه را ویرایش و ذخیره کرد؛ بعد از بارگیریِ مجدد،
اضافه‌هایش نبود. علت: برای همگام‌سازی با «آخرین مصوبه»، این یک فیلد به‌صورت
`db || saved || default` بارگیری می‌شد — تنها فیلدِ متنیِ DB-first — و نسخهٔ
استخراجیِ DB بی‌صدا جای متنِ ذخیره‌شدهٔ کاربر می‌نشست.

## 💡 راه‌حل / Solution

- برای فیلدی که کاربر مستقیم ویرایش و ذخیره می‌کند: **snapshot کاربر همیشه
  برنده**؛ نسخهٔ DB را جداگانه نگه دار و اگر متفاوت بود، toast + دکمهٔ صریحِ
  «از آخرین مصوبه» (با confirm) بده — همگام‌سازی opt-in، نه خاموش.
- DB-first فقط برای داده‌هایی مجاز است که کاربر مالکِ متنش نیست (ردیف‌های
  تسهیلات از مصوبه — تصمیمِ آگاهانه و مستند).

## ⚠️ نکات حیاتی / Pitfalls

- «فقط یک فیلد استثناست» دقیقاً همان‌جایی است که گم‌شدنِ داده گزارش می‌شود؛
  در loadAccountها ترتیبِ اولویتِ هر فیلد را کنار هم نگاه کن.
- جایگزینیِ خاموش را هرگز با «دادهٔ جدیدتر بهتر است» توجیه نکن — جدیدتر از
  نظرِ pipeline، نه از نظرِ کاربر.

## 🔁 چطور در جای دیگر اعمال کنیم / How to Apply Elsewhere

- [ ] هر فیلدِ editable که منبعِ همگام‌سازیِ خودکار دارد: saved-first + پیشنهادِ
  صریحِ نسخهٔ منبع.
- [ ] تستِ E2E: snapshot ≠ DB ⇒ متنِ snapshot چاپ شود و دکمهٔ همگام‌سازی ظاهر.
