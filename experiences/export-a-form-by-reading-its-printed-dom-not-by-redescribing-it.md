# خروجیِ Word/Excel از یک فرم: DOMِ چاپی را بخوان، فرم را دوباره توصیف نکن

## 🎯 چالش / Challenge

یک فرمِ جدولیِ پیچیده روی صفحه هست (بخش‌های بنددار، سرستون، ردیف‌های افزودنی،
ستون‌هایی که فقط روی صفحه‌اند) و کاربر می‌خواهد «**دقیقاً به همین شکل**» در
Word و Excel دانلودش کند.

راهِ بدیهی — نوشتنِ ساختارِ فرم داخلِ دو خروجی‌گیر — سه نسخهٔ موازی از یک چیدمان
می‌سازد. اولین باری که کسی یک ردیف به فرم اضافه کند، خروجی‌ها ساکت عقب می‌مانند
و کسی نمی‌فهمد تا وقتی فایل برای مشتری فرستاده شود.

## 💡 راه‌حل / Solution

**یک خواننده از DOM، دو رندرکننده.**

1. یک ماژول، فرمِ زنده را می‌خواند و به یک **spec خنثی** تبدیل می‌کند
   (بلوک‌ها، ردیف‌ها، سلول‌های ادغام‌شده، نسبتِ عرضِ ستون‌ها، رنگ‌ها).
2. خروجی‌گیرِ Word و خروجی‌گیرِ Excel هر دو **فقط** همان spec را می‌خوانند.
3. بخشی که فردا به فرم اضافه شود، خودش در هر دو خروجی ظاهر می‌شود.

**آنچه صادر می‌شود، نمای «چاپ» است، نه نمای «صفحه».** صفحه از قبل تصمیم گرفته
چه چیزی روی کاغذ می‌رود؛ همان قاعده را اجرا کن:
- حذف: ستون‌های ابزار، هرچه `screen-only` است، و **ردیف‌هایی که کاربر خودش از
  چاپ حذف کرده**؛
- نگه‌داشتن: عناصرِ `print-only` (مثلاً متنی که جایگزینِ یک dropdown می‌شود);
- ویجت‌ها به شکلِ کاغذی: `input` → مقدارش، `checkbox` → ☑/☐،
  `select` → متنِ گزینهٔ انتخابی.

اگر کاربر ردیفی را از چاپ حذف کرده و خروجی آن را برگرداند، خروجی «همانی که
می‌بیند» نیست — این تنها چیزی است که خواسته شده بود.

## 🧪 نمونه کد (Anonymized)

**شبکه را باز کن، بعد ستون بینداز.** ستونِ فقط-صفحه‌ای که حذف می‌شود، `colspan`
هر سلولِ بنددار را هم عوض می‌کند:

```ts
// هر سلول را در شبکهٔ واقعی (با colspan/rowspan) جای‌گذاری کن
const { anchors, ncols } = gridOf(table)

// ستونی که فقط روی صفحه است: همیشه یک سلولِ تک‌عرض در همان ستون دارد
const drop = new Set<number>()
anchors.forEach(r => r.forEach(a => {
  if (a.cols === 1 && a.td.classList.contains('tools')) drop.add(a.c0)
}))

// span را دوباره حساب کن، نه اینکه از colspan اصلی کپی کنی
const span = range(a.c0, a.cols).filter(c => !drop.has(c)).length
if (!span) return                       // سلولی که فقط در ستون‌های حذف‌شده بود
```

عرضِ ستون‌ها را **اندازه بگیر**، حدس نزن — `getBoundingClientRect()` روی یک
سلولِ تک‌عرضِ هر ستون، بعد نرمال‌سازی به نسبت.

## 🧩 یک برگه، یک شبکه: بخش‌هایی با تعدادِ ستونِ متفاوت

مهم‌ترین تلهٔ «فرمِ چندجدولی → اکسل»: worksheet فقط **یک** شبکهٔ ستونی دارد،
ولی فرم چند جدول با تعدادِ ستونِ متفاوت است. اگر همه را روی ستون‌های **پهن‌ترین**
جدول بنشانی:

- جدول‌های باریک‌تر وسطِ برگه تمام می‌شوند و یک **ستونِ خالی** کنارِ لبه می‌ماند؛
- نوارهای بنددار کوتاه تمام می‌شوند → لبهٔ راستِ دندانه‌دار؛
- جدولی با ستون‌های خیلی کم (مثلاً دوتایی) داخلِ باریک‌ترین ستون **له** می‌شود
  و متنش بریده می‌شود.

راه‌حل: **اجتماعِ مرزها**. مرزهای ستونیِ هر جدول را به‌صورتِ کسری از عرض حساب
کن، همه را یکی کن، و هر سلول را روی بازه‌های حاصل نگاشت کن:

```python
bounds = cumulative(widths)                 # [0, .1, .4, 1.0]
marks  = union(bounds for every table)      # مرزهای مشترک
grid   = [m for m in sorted(marks) if m - prev >= SNAP]   # اسنپِ مرزهای نزدیک
# هر سلول: از نزدیک‌ترین مرز به ابتدایش تا نزدیک‌ترین مرز به انتهایش
```

دو نگهبانِ لازم:
1. **تلورانسِ اسنپ** — وگرنه جدول‌هایی که مرزهایشان تقریباً یکی است، هرکدام
   مرزِ خودشان را می‌آورند و برگه پر از ستونِ موییِ غیرقابلِ‌ویرایش می‌شود.
2. **سقفِ تعدادِ ستون** — باریک‌ترین مرزهای میانی را حذف کن تا از سقف رد نشود.

و هر ردیفِ کوتاه‌تر: **آخرین سلولش را تا لبه بکش**، نه اینکه سلولِ خالیِ کادردار
کنارش بگذاری — همان «ستونِ اضافه» را می‌سازد که می‌خواستی از بین ببری.

## ⚠️ نکات حیاتی / Pitfalls

- **openpyxl هنگام `merge_cells` رنگِ سلول‌های پوشش‌داده‌شده را پاک می‌کند.**
  پس ترتیب برعکسِ چیزی است که به‌نظر می‌رسد: **اول merge، بعد استایل**. استایلِ
  قبل از merge دور ریخته می‌شود و نوارِ بنددار فقط در ستونِ اولش رنگی درمی‌آید.
- **خواندنِ فایل با خودِ openpyxl این را نشان نمی‌دهد.** خواننده‌اش برای هر ستونِ
  پوشش‌داده‌شده یک `MergedCell` بی‌استایل برمی‌گرداند، چه رنگ نوشته شده باشد چه
  نه. تست باید `xl/styles.xml` را بخواند (`fillId` واقعی) وگرنه **هم باگ را
  می‌بیند وقتی نیست، هم نمی‌بیند وقتی هست**.
- **در Word، جدول‌های پشتِ‌سرِ هم به هم می‌چسبند.** بینشان یک پاراگرافِ خالی
  بگذار وگرنه کلِ فرم یک شبکهٔ واحد می‌شود.
- **سلولِ خالی در OOXML نامعتبر است** — یک پاراگرافِ خالی بگذار، وگرنه Word فایل
  را «تعمیر» می‌کند و کاربر با پیامِ خرابی بازش می‌کند.
- **جمعِ عرضِ ستون‌ها باید دقیق باشد**؛ باقی‌ماندهٔ گردکردن را به ستونِ آخر بده،
  وگرنه Word کلِ جدول را بی‌صدا مقیاس می‌کند و ستون‌ها با صفحه هم‌تراز نمی‌شوند.
- **تزریقِ فرمول در Excel:** سلولی که با `= + - @` شروع شود اجرا می‌شود. نامِ
  مشتری واقعاً می‌تواند این‌طور شروع شود؛ یک `'` جلویش بگذار.
- **جهت (bidi):** در یک سندِ لاتین، هیچ عنصرِ `w:rtl` نگذار — در OOXML صرفِ
  **وجودش** یعنی روشن. متنِ فارسی داخلِ پاراگرافِ LTR بدونِ علامت درست رندر
  می‌شود؛ همان کاری که مرورگر می‌کند.

## 🔁 چطور در جای دیگر اعمال کنیم / How to Apply Elsewhere

1. آیا چیدمان جای دیگری هم توصیف شده؟ اگر بله، خروجی‌گیر باید از **همان**
   منبع بخواند، نه یک کپی.
2. قاعدهٔ «چه چیزی روی کاغذ می‌رود» کجاست؟ خروجی باید **همان** را اجرا کند،
   نه یک قاعدهٔ جدید.
3. تقسیمِ کار: کلاینت توصیف می‌کند، سرور با کتابخانهٔ واقعی رندر می‌کند —
   با کلمپ کردنِ اندازه‌ها و پاک‌سازیِ متن، چون همهٔ ورودی نامطمئن است.
4. تست را روی **فایلِ نوشته‌شده** بنویس، نه روی خواندنِ دوبارهٔ همان کتابخانه.
5. آخرش در مرورگرِ واقعی دکمه را بزن و فایل را باز کن — ساختِ بی‌خطا یعنی
   فایل ساخته شد، نه اینکه درست است.
