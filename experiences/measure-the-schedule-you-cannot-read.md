# برنامه‌ای که نمی‌توانی بخوانی را اندازه بگیر

## 🎯 چالش / Challenge

کاربر دکمه‌ای می‌زند و می‌پرسد «چند دقیقهٔ دیگر انجام می‌شود؟». کارِ واقعی را یک
**زمان‌بندِ بیرونی** انجام می‌دهد (Routine در یک سرویسِ دیگر، cron روی ماشینِ
دیگر، صفِ یک تیمِ دیگر) که برنامه‌اش در این مخزن نیست و این سرور نمی‌تواند
بخواندش.

راهِ وسوسه‌انگیز: عدد را در کد بنویس — «هر ساعت، دقیقهٔ ۲۳». این عدد فقط تا
**اولین ویرایشِ آن زمان‌بند** درست است، و بعد بی‌سروصدا دروغ می‌گوید. کاربر روی
شمارشِ معکوس برنامه می‌ریزد، پس **شمارشِ معکوسِ غلط از نبودنش بدتر است**.

## 💡 راه‌حل / Solution

**۱) زمان‌بند خودش به تو خبر می‌دهد — فقط ثبتش کن.** تقریباً همیشه یک تماسِ
تکراری وجود دارد که در **هر** اجرا برقرار می‌شود (حتی وقتی کاری نیست). همان
ضربانِ ساعت است:

```python
@router.post("/queue/claim")
async def claim(...):
    if not is_the_worker(user):        # فقط کارگر، نه هر بیننده‌ای
        raise HTTPException(403)
    await note_round(db)               # پیش از هر کاری — اجرای شکست‌خورده هم «آمد»
    ...
```

مهم: تماسِ **کارگر** را ثبت کن، نه خواندنِ صفحه توسطِ کاربر؛ وگرنه رفرشِ خودِ
کاربر ضربان جعل می‌کند و شمارش به دوری اشاره می‌کند که هرگز نمی‌آید.

**۲) آهنگ را از فاصله‌ها دربیاور، نه از میانگینِ خام.**

```python
gaps  = [(b - a).total_seconds() for a, b in zip(stamps, stamps[1:])]
every = median(gaps)                       # میانه، نه میانگین: یک اجرای دیرکرده اثر نگذارد
if 45*60 <= every <= 75*60:                # «ساعتی» است
    at = next_occurrence_of(mode_of_minute(stamps))   # دقیقهٔ غالب، نه آخرین دقیقه
else:
    at = stamps[-1] + every                # آهنگِ دیگر: از آخرین ضربان گام بردار
```

در تساویِ دقیقه‌ها، **نسخهٔ جدیدتر برنده** باشد؛ وگرنه برنامه‌ای که عوض شده را
میانگین می‌گیری و جواب برای هر دو غلط می‌شود.

**۳) جواب باید بگوید چقدر مطمئن است.** سه حالت، سه رفتار:

| حالت | یعنی | چه بگو |
|---|---|---|
| `observed` | دیده‌ایم | وقتِ دقیق |
| `assumed` | هنوز چیزی ثبت نشده | همان + «تخمینی» |
| `stale` | چند دور است نیامده | **هیچ وعدهٔ زمانی نده** — «ممکن است خاموش باشد» |

`stale` نکتهٔ اصلی است: زمان‌بندِ خاموش نباید تا ابد «۱۹ دقیقهٔ دیگر» وعده بدهد.

**۴) سرور یک «لحظه» می‌فرستد؛ «ساعت» را مرورگر می‌سازد.** سروری که زمان را
قالب‌بندی کند باید منطقهٔ زمانی را حدس بزند:

```ts
// ISO UTC از سرور → ساعتِ دیوارِ خودِ کاربر
const d = new Date(iso)
`${String(d.getHours()).padStart(2,'0')}:${String(d.getMinutes()).padStart(2,'0')}`
```

**۵) شمارشِ روی صفحهٔ باز باید حرکت کند.** از **لحظه** دوباره حساب کن، نه از
عددِ دقیقه‌ای که سرور فرستاد؛ وگرنه صفحه‌ای که یک ساعت باز مانده همان عددِ اولیه
را نشان می‌دهد. یک تایمرِ مشترک برای کلِ صفحه، نه یکی برای هر نشان.

**۶) جدولِ تازه نساز اگر یک کلید/مقدارِ موجود کافی است.** لاگِ ضربان چند مهر
زمانی است؛ در جدولِ تنظیماتِ موجود بنشان که **از قبل در بکاپ هست**. جدولِ تازه
یعنی سطحِ تازه برای گسترش (بکاپ، بایگانی، audit) بی‌آنکه چیزی به دست بیاید.

## ⚠️ نکات حیاتی / Pitfalls

- **صفِ خالی هم یک اجراست.** اگر فقط اجراهای «کارکرده» را ثبت کنی، یک هفتهٔ آرام
  شبیهِ زمان‌بندِ خراب می‌شود.
- **ضربان را پیش از کار ثبت کن** تا اجرایی که بعداً شکست می‌خورد هم «آمد» شمرده
  شود — سؤال این است «کِی می‌آید»، نه «کِی موفق می‌شود».
- **میانگین نه، میانه.** یک اجرای دو ساعت دیرکرده میانگین را خراب می‌کند.
- **هرگز عددِ منفی یا صفر نشان نده**؛ «۰ دقیقه» را کاربر «دارد انجام می‌شود»
  می‌خواند و بعد یک ساعت منتظر می‌ماند.
- **رشتهٔ نتیجه را تست کن، نه فقط حساب را.** جمله چیزی است که کاربر می‌خواند:
  رقمِ محلی، صفرِ پیش‌رو، «فردا» بعد از نیمه‌شب، و اینکه در حالتِ `stale` هیچ
  عددی وعده داده نشود.
- **متنِ آمیختهٔ RTL/عدد را داخلِ `dir` صریح بگذار** — build سبز این را نمی‌گیرد.

## 🔁 چطور در جای دیگر اعمال کنیم / How to Apply Elsewhere

1. بپرس «کدام تماس در **هر** اجرا برقرار می‌شود؟» — همان ضربانِ توست.
2. فقط تماسِ کارگر را ثبت کن، و پیش از کار.
3. آهنگ را با میانه دربیاور؛ برای حالتِ ساعتی، دقیقهٔ غالب را بگیر.
4. سه حالتِ `observed/assumed/stale` را برگردان و UI هر سه را جدا نشان بدهد.
5. لحظه را بفرست، ساعت را سمتِ کاربر بساز، و روی صفحهٔ باز تیک بزن.

## Update 2026-10-07 — وقتی خودِ برنامه عوض شد (ساعتی ← هر ۳ ساعت، v179)

اندازه‌گیری درست بود، ولی سه فرضِ پنهانِ «برنامهٔ ثابت» با تغییرِ برنامه رو شد:

1. **میانهٔ همهٔ تاریخچه = کُند در تغییر.** با ۱۲ تقه، میانه تا ۶ فاصلهٔ تازه لازم داشت ⇒
   ~۱۸ ساعت «ساعتی» نشان می‌داد. میانهٔ **۳ فاصلهٔ آخر**: یک جاافتادن را تحمل می‌کند و
   تغییر را در دو دور می‌گیرد.
2. **«گذشت» ≠ «رفت».** دورِ چند دقیقه دیر، پاسخ را به نوبتِ بعدی (۳ ساعت بعد) می‌پراند.
   پنجرهٔ مهلت (کمینهٔ ۳۰ دقیقه و یک‌سوم دوره) با وضعیتِ جدا `due` ⇒ «در راه است». و
   نوبتی که تقه‌اش آمده دوباره «در راه» حساب نشود (تستِ موجود همین را گرفت).
3. **اجرای دستی لنگرِ برنامه نیست.** cron همیشه روی یک دقیقه می‌افتد؛ فقط تقه‌های همان
   دقیقه (±۳) برنامه‌اند و بقیه برای «آخرین بار دیده شد» به کار می‌روند، نه برای پیش‌بینی.

درسِ کلی: آزمونِ «برآوردگرِ زمان‌بندی» باید سناریوی **تغییرِ برنامه**، **تأخیر** و **اجرای
بی‌نوبت** را هم داشته باشد، نه فقط حالتِ پایدار.
