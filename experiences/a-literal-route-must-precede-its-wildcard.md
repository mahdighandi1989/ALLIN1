# مسیرِ ثابت باید قبل از مسیرِ پارامتری اعلام شود

## 🎯 چالش / Challenge

یک صفِ «فوری» ساختیم و `GET /urgent` را — طبیعی‌ترین جا — کنارِ بقیهٔ
endpointهای همان قابلیت، پایینِ فایل گذاشتیم. بالاترش، از ماه‌ها پیش،
`GET /{report_id}` بود.

نتیجه: `/urgent` هرگز اجرا نشد. روتر رشتهٔ `urgent` را به‌عنوانِ **مقدارِ**
`report_id` پذیرفت و جوابِ «گزارشی با این شناسه نیست» داد. یعنی خطا **۴۰۴** بود،
نه ۵۰۰ — دقیقاً شکلِ یک پاسخِ سالم برای یک شناسهٔ ناموجود. هیچ لاگی فریاد نزد.

این خطا را **تست** گرفت، نه خواندنِ کد: چشم وقتی دو دکوراتور را در دو نقطهٔ دورِ
یک فایلِ هزارخطی می‌بیند، تقدم‌شان را نمی‌سنجد.

## 💡 راه‌حل / Solution

> **در هر روترِ «اولین تطابق برنده است» (FastAPI/Starlette، Express، Flask با
> converterها، Gin…)، هر مسیرِ ثابت باید بالاتر از مسیرِ پارامتریِ هم‌شکلش
> اعلام شود — و کنارش یک کامنت بگذار که چرا آنجاست.**

جابه‌جایی کافی نیست؛ نفرِ بعدی که endpoint اضافه می‌کند دوباره همان‌جا می‌نویسد.
کامنتِ «این باید بالای X بماند» بخشی از راه‌حل است.

و مهم‌تر: **برای هر مسیرِ ثابتِ تازه یک تستِ status-code بنویس.** تست چیزی را
می‌گیرد که مرور نمی‌گیرد، چون تست ترتیبِ واقعیِ ثبت‌شده را اجرا می‌کند نه ترتیبِ
ذهنیِ خواننده را.

## 🧪 نمونه کد (Anonymized)

```python
# ❌ /items/archived هرگز اجرا نمی‌شود
@router.get("/items/{item_id}")
async def get_item(item_id: str): ...

@router.get("/items/archived")      # مرده — «archived» می‌شود item_id
async def archived(): ...

# ✅
# NOTE — must stay ABOVE «/{item_id}»: a literal path declared after a path
# parameter is never reached.
@router.get("/items/archived")
async def archived(): ...

@router.get("/items/{item_id}")
async def get_item(item_id: str): ...
```

```python
# تستی که این را می‌گیرد (و فقط این را)
async def test_literal_route_is_not_shadowed(client):
    r = await client.get("/items/archived")
    assert r.status_code == 200          # نه ۴۰۴
    assert "items" in r.json()           # شکلِ صف، نه شکلِ «یک آیتم»
```

## ⚠️ نکات حیاتی / Pitfalls

- **علامتِ خطا ۴۰۴ است، نه ۵۰۰.** یعنی شبیهِ رفتارِ درست است. اگر فقط دنبالِ
  استثنا در لاگ بگردی، پیدایش نمی‌کنی.
- **تعدادِ قطعاتِ مسیر مهم است.** `/{id}/urgent` جلوی `/urgent/claim` را
  نمی‌گیرد (قطعهٔ دوم باید عیناً `urgent` باشد)، ولی `/{id}/{action}` می‌گیرد.
  قبل از اینکه خیالت راحت شود، قطعه‌به‌قطعه تطبیق بده.
- **جای طبیعی برای خواندن ≠ جای درست برای ثبت.** وسوسه می‌شوی endpointهای یک
  قابلیت را کنار هم بگذاری؛ ترتیبِ روتر این اجازه را نمی‌دهد. گروه‌بندیِ خوانا را
  با کامنت جبران کن، نه با جابه‌جاییِ دکوراتور.
- **فریم‌ورک‌هایی که مسیرها را رتبه‌بندی می‌کنند** (بعضی روترها ثابت را همیشه بر
  پارامتری مقدم می‌کنند) این مشکل را ندارند — ولی به فرض تکیه نکن؛ یک تست بنویس
  و بگذار خودِ فریم‌ورک جوابت را بدهد.

## 🔁 چطور در جای دیگر اعمال کنیم / How to Apply Elsewhere

1. در هر فایلِ روتر، فهرستِ مسیرها را به ترتیبِ **اعلام** بیرون بکش
   (`grep -n '@router\.'`) — نه به ترتیبِ الفبا.
2. هر مسیرِ ثابتی که بعد از یک مسیرِ پارامتریِ هم‌طولِ هم‌پیشوند آمده، مرده است.
3. جابه‌جا کن + کامنتِ «must stay ABOVE …» بگذار.
4. برای هر مسیرِ ثابت یک تستِ status-code بنویس؛ این تست ارزان است و دقیقاً همان
   چیزی را می‌گیرد که مرورِ چشمی از دست می‌دهد.
5. وقتی endpointِ تازه اضافه می‌کنی، قدمِ ۱ را دوباره اجرا کن — این بازرسی
   یک‌بارمصرف نیست.
