# Get the bytes before theorising

## 🎯 چالش / Challenge

کاربر اسکرین‌شاتی می‌فرستد که در آن متن به‌هم‌ریخته است: به‌جای `Account Name`
نوشته `ß½½±«²¬ Ò¿³»`. دو توضیحِ کاملاً متفاوت ممکن است:

- **داده خراب است** — کدپوینت‌های غلط در حافظه/دیتابیس نشسته‌اند.
- **رندر خراب است** — داده سالم است و فقط **فونت** گلیفِ اشتباه می‌کشد.

از روی تصویر **نمی‌شود** این دو را از هم تشخیص داد. و اگر اشتباه انتخاب کنی،
می‌توانی چند نسخه را صرفِ ساختنِ راه‌حلِ بی‌عیب برای مسئلهٔ اشتباه کنی.

خطرِ ویژه: وقتی کاراکترها را **از روی عکس می‌خوانی**، ناخودآگاه همان‌هایی را
«می‌بینی» که فرضیه‌ات لازم دارد. بعد رمزگشایی می‌کنی و جوابِ کاملاً معناداری
می‌گیری («Statement NO»!) و این را **تأییدِ** فرضیه می‌شماری. در حالی که فقط
استدلالِ دورانی کرده‌ای: خودت ورودی را طوری خواندی که خروجی درست دربیاید.

## 💡 راه‌حل / Solution

**۱) قبل از هر نظریه‌ای، ground truth بگیر.** یک درخواستِ ده‌ثانیه‌ای از کاربر:
«همان متن را انتخاب کن، کپی کن، و اینجا پیست کن.» نتیجه قاطع است:

- **پیست خراب بود** ⇒ داده خراب است ⇒ دنبالِ مسیرِ ورودِ داده بگرد.
- **پیست سالم بود** ⇒ DOM سالم است ⇒ **مشکل صددرصد رندر است** (فونت/CSS).

هیچ تحلیلِ هوشمندانه‌ای جای این یک قدم را نمی‌گیرد.

**۲) نشانه‌هایی که به فونت اشاره می‌کنند** (و من اولش اشتباه تفسیرشان کردم):
- **ارقام سالم‌اند ولی حروف خراب** ⇒ به‌شدت بوی `unicode-range` می‌دهد: یک
  `@font-face` که فقط محدودهٔ حروف را پوشش می‌دهد، ارقام را به فونتِ دیگری
  واگذار می‌کند. (من این را نشانهٔ «فقط حروف داده‌شان خراب شده» گرفتم — غلط.)
- **فقط یک زبان/اسکریپت خراب است** و بقیهٔ صفحه سالم.
- **فقط روی دستگاهِ یک کاربر** خراب است و روی بقیه سالم.
- **سندهای قبلی سالم بودند** — چون آن نوع محتوا (مثلاً متنِ لاتین) را نداشتند.

**۳) ریشهٔ رایجِ این کلاس از باگ‌ها: `src: local(...)`.**

```css
@font-face{font-family:'X';src:local('Times New Roman'),local('Times');
           unicode-range:U+0041-005A,U+0061-007A}
```

`local()` یعنی «فونت را **به نام** از دستگاهِ بیننده بگیر». روی ماشینی که آن نام
به یک فونتِ legacy/دست‌کاری‌شده/خراب رسیده باشد، برنامه‌ات متنِ کاملاً سالم را
به‌شکلِ آشغال نشان می‌دهد و **هیچ لاگ و هیچ تستِ سبزی** آن را نمی‌گیرد.

**۴) راه‌حل: فونت را خودت ارسال کن.** `src: url(...)` با فایلِ subsetشده‌ی
کنارِ برنامه، **بدونِ هیچ `local()` fallback** — چون بردنِ فونتِ محلی دقیقاً
همان باگ است. برای جایگزینیِ بی‌دردسرِ یک فونتِ رایج، یک جایگزینِ
**metric-compatible** انتخاب کن (مثلاً Liberation Serif برای Times New Roman،
یا Arimo برای Arial) تا شکستِ خطوط و عرضِ ستون‌های اسنادِ موجود تغییر نکند.

**۵) قرارداد را با تست قفل کن.** این یک باگِ **رندری** است؛ build سبز نمی‌گیردش.
پس یک تستِ ساده روی سورس بنویس: «هیچ `src: local(` در این صفحه نباشد»،
«هر `url()` واقعاً وجود داشته باشد»، «`unicode-range` همان باشد».

## 🧪 نمونه کد (Anonymized)

subset کردن و ارسالِ فونت (fontTools):

```python
from fontTools import subset
subset.main([
    "/usr/share/fonts/truetype/liberation/LiberationSerif-Regular.ttf",
    "--unicodes=U+0020-007E,U+00A0-024F",
    "--flavor=woff2", "--layout-features=kern,liga",
    "--output-file=public/fonts/ltr-regular.woff2",
])   # ~40 KB per weight
```

```css
/* shipped with the app — what the user sees no longer depends on their PC */
@font-face{font-family:'LtrMix';src:url('/fonts/ltr-regular.woff2') format('woff2');
           font-weight:400;font-display:swap;
           unicode-range:U+0041-005A,U+0061-007A,U+00C0-024F}
```

تستی که برگشتِ باگ را می‌بندد:

```ts
const PAGE = readFileSync(join(__dirname, 'page.tsx'), 'utf8')
it('never sources a font from the viewer machine', () => {
  expect(PAGE).not.toMatch(/src:\s*local\(/)
})
it('every url() it references really exists', () => {
  for (const [, f] of PAGE.matchAll(/url\('\/fonts\/([^']+)'\)/g))
    expect(statSync(join(FONT_DIR, f)).size).toBeGreaterThan(5000)
})
```

## ⚠️ نکات حیاتی / Pitfalls

- **خواندنِ کاراکتر از روی عکس، داده نیست — حدس است.** `½` و `œ`، `´` و `Ž`،
  `ß` و `B` در اندازهٔ کوچک تفکیک‌ناپذیرند. اگر فرضیه‌ات به هویتِ دقیقِ یک گلیف
  وابسته است، آن گلیف را باید از متنِ واقعی بگیری.
- **«رمزگشایی جواب داد» اثبات نیست** وقتی خودت ورودیِ رمزگشایی را از روی حدس
  ساخته‌ای. آزمونِ واقعی این است که **پیش‌بینی** کنی و با دادهٔ مستقل بسنجی.
- **مرحلهٔ استقرار را قبل از فرضیهٔ بعدی ثابت کن.** یک برچسبِ نسخهٔ **قابلِ
  دیدن** در UI بگذار و به‌روز نگهش دار؛ بدونِ آن، «هنوز خراب است» و «هنوز
  دیپلوی نشده» از هم قابلِ تفکیک نیستند و یک دور کامل هدر می‌رود.
- **تکرارِ یک اصلاح در جای دیگر، اصلاحِ ریشه نیست.** وقتی دو بار جای فراخوانی را
  عوض کردی و نتیجه فرق نکرد، **فرضیه** را زیرِ سؤال ببر، نه محلِ فراخوانی را.
- **فونتِ اسکریپتِ اصلی را هم چک کن.** اگر لاتین با `local()` می‌آید، احتمالاً
  فارسی/عربی هم همین‌طور است — همان شکنندگی، فقط هنوز بروز نکرده.
- **کدی که برای تشخیصِ غلط نوشته‌ای را کورکورانه پاک نکن**، ولی صریحاً ثبت کن که
  آن باگ را حل نکرد — وگرنه نفرِ بعدی فکر می‌کند حلش کرده.

## 🔁 چطور در جای دیگر اعمال کنیم / How to Apply Elsewhere

1. از کاربر **متنِ کپی‌شده** بخواه، نه اسکرین‌شات (یا خودت از DOM/DB بخوان).
2. سالم بودنِ کپی ⇒ رندر؛ خراب بودنِ کپی ⇒ داده. مسیر را همین‌جا انتخاب کن.
3. برای مسیرِ رندر: `@font-face`ها، `font-family`های inline، `unicode-range`ها.
4. هر `local()` را با فایلِ ارسالی جایگزین کن؛ جایگزینِ metric-compatible بگیر.
5. قرارداد را با تستِ سورس قفل کن (build سبز این کلاس را نمی‌گیرد).
6. یک برچسبِ نسخهٔ قابلِ دیدن نگه دار تا «دیپلوی شد؟» هیچ‌وقت سؤال نباشد.
