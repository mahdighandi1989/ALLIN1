# پیش‌فرضی که شبیهِ تصمیم است، رکورد را خراب می‌کند

## 🎯 چالش / Challenge

یک فیلدِ دسته‌بندی (مثلاً «حقیقی / حقوقی»، «فعال/غیرفعال»، «داخلی/خارجی») پیش‌فرضِ
«معقول» گرفت:

```python
account_type = Column(Enum(AccountType), default=AccountType.RETAIL)
```

و ایمپورتِ انبوه هم همان کار را کرد:

```python
a = str(rec.get("account_type") or "retail").lower()   # ستون نبود ⇒ retail
```

نتیجه این است که دیتابیس دیگر نمی‌تواند این دو را از هم تشخیص دهد:

| واقعیت | مقدارِ ذخیره‌شده |
|---|---|
| «این حساب شخصِ حقیقی است» (کسی تصمیم گرفت) | `retail` |
| «هیچ‌کس تعیین نکرده» (پیش‌فرض) | `retail` |

این یک خطای «داده‌ی غلط» نیست؛ **نابودیِ اطلاعات** است — آن‌هم بی‌صدا، در پهن‌ترین
مسیرِ ورودیِ سیستم. هیچ تستی قرمز نمی‌شود، هیچ لاگی چیزی نمی‌گوید، و ماه‌ها بعد
کاربر می‌گوید «چرا برای یک شرکت فرمِ شخصی باز می‌کند؟».

**نشانهٔ تشخیصیِ قطعی:** کدی که می‌گوید «اگر تعیین نشده بود، از کاربر بپرس»
تبدیل به **کدِ مرده** می‌شود — چون هرگز تعیین‌نشده وجود ندارد.

## 💡 راه‌حل / Solution

1. **«نمی‌دانم» یک مقدارِ درجه‌یک است، نه غیابِ مقدار.** یک عضوِ صریح
   (`UNKNOWN`) به enum اضافه کن و پیش‌فرض را همان بگذار.
2. **هر جایی که مقدار می‌سازد را پیدا کن، نه فقط مدل را.** ایمپورت‌ها،
   `or "default"`ها، و نگاشت‌های فرم. `grep` روی نامِ فیلد، نه روی نامِ مدل.
3. **دادهٔ موجود را بازنویسی نکن.** سیستم نمی‌داند کدام مقدارها تصمیمِ واقعی
   بوده‌اند؛ بازنویسی، حدسی دیگر روی حدسِ قبلی است.
4. **یک طبقه‌بندِ مبتنی بر شواهد بساز که فقط نظر می‌دهد.** از فیلدهایی که
   خودِ دیتابیس دارد، با **شواهدِ مثبت فقط**؛ نبودِ شاهد ⇒ `unknown`، نه حدس.
5. **دو مشکل را هرگز یکی نکن:** «تصمیم گرفته نشده» و «تصمیم با شواهد نمی‌خواند»
   دو یافتهٔ جدا با دو راه‌حلِ جدا هستند. یکی‌کردنشان عددِ واقعی را پنهان می‌کند.
6. **اصلاح، بازبینی‌محور:** فهرست + دلیل + دکمهٔ اعمالِ تک‌به‌تک. هیچ سوییچِ
   «همه را درست کن» روی heuristic.
7. **قاعدهٔ پایش اضافه کن**، وگرنه دفعهٔ بعد هم ساکت می‌ماند.

## 🧪 نمونه کد (Anonymized)

```python
class Kind(str, Enum):
    A = "a"; B = "b"
    UNKNOWN = "unknown"      # «هیچ‌کس تعیین نکرده» — یک وضعیتِ واقعی

kind = Column(Enum(Kind), default=Kind.UNKNOWN)      # نه Kind.A

def from_listing(rec) -> str:
    v = str(rec.get("kind") or "").strip().lower()
    return v if v in VALID else "unknown"             # نه "a"
```

طبقه‌بند — فقط نظر، با دلیل:

```python
@dataclass
class Verdict:
    guess: str = UNKNOWN
    confidence: str = "none"      # high | medium | low | none
    reasons: list = field(default_factory=list)
    counter_reasons: list = field(default_factory=list)

def classify(**evidence) -> Verdict:
    strong, weak = [], []
    if evidence["licence_no"]:  strong.append("جوازِ تجاری فقط برای شخصیتِ حقوقی صادر می‌شود")
    if evidence["partners"]:    strong.append("شریکِ ثبت‌شده دارد")
    # شواهدِ ضعیف فقط وقتی حرف می‌زنند که شاهدِ قوی نباشد
    if evidence["id_doc"] and not strong: weak.append("فقط مدرکِ هویتِ شخصی دارد")
    ...
    return Verdict(...)          # هیچ نوشتنی

def disagrees(stored, v: Verdict) -> bool:
    """تصمیمِ ذخیره‌شده با شاهدِ مطمئن جور نیست؟ «تعیین‌نشده» تناقض نیست."""
    if is_undecided(stored) or not v.decided or v.confidence in ("none", "low"):
        return False
    return family(stored) != family(v.guess)
```

## ⚠️ نکات حیاتی / Pitfalls

- **شاهدِ ضعیف را با شاهدِ قوی قاطی نکن.** پروندهٔ یک شرکت به‌درستی پاسپورتِ
  *مدیرش* را دارد — فرمِ شرکتی اصلاً فیلدِ «Manager Emirates ID» دارد. مدرکِ
  هویتی فقط **در نبودِ** هر شاهدِ شرکتی معنا دارد.
- **تطبیقِ کلمه، نه زیررشته.** `EST` داخلِ `Ernesto` و `CO` داخلِ `Cotton` در
  مقیاسِ چندهزار رکورد فاجعه می‌سازد. `\b…\b`.
- **مقدارِ زیرمجموعه تناقض نیست:** اگر `sme` زیرمجموعهٔ `corporate` است،
  «`sme` ذخیره شده ولی شواهد می‌گوید corporate» نباید یافته باشد.
- **گزارشِ سیل‌آسا خوانده نمی‌شود:** اگر ۴۰۰۰ رکورد ایراد دارند، ۲۵ نمونه +
  یک خطِ جمع‌بندی بده، نه ۴۰۰۰ یافته که بقیهٔ گزارش را دفن می‌کند.
- **تستی که پیش‌فرضِ غلط را تثبیت کرده بود را پیدا کن.** این‌جا دو تست دقیقاً
  `assert customer.account_type == RETAIL` داشتند؛ آن‌ها باگ را **قفل** کرده
  بودند. تست را به قراردادِ درست به‌روز کن و دلیلش را همان‌جا بنویس.

## 🔁 چطور در جای دیگر اعمال کنیم / How to Apply Elsewhere

برای هر فیلدِ دسته‌بندی/وضعیت این‌ها را بپرس:

1. اگر کسی تعیین نکند، چه ذخیره می‌شود؟ اگر یک مقدارِ **معتبرِ دامنه** است ⇒ باگ.
2. آیا می‌شود «تعیین‌نشده» را از «تعیین‌شده» تشخیص داد؟ اگر نه ⇒ باگ.
3. کدی هست که می‌گوید «اگر خالی بود بپرس»؟ آیا اصلاً اجرا می‌شود؟ اگر نه،
   همان‌جا ثابت می‌شود که پیش‌فرض اطلاعات را بلعیده.
4. چند مسیرِ دیگر همین مقدار را می‌سازند؟ (`or "x"` را grep کن.)
5. آیا دیتابیس شواهدی دارد که بشود با آن تصمیم را سنجید؟ اگر بله، گزارشش کن.

## Update 2026-09-28 — شاهدی که فقط *به‌نظر* قطعی است

قوی‌ترین قاعدهٔ طبقه‌بند غلط بود، و **مالک گیرش انداخت، نه بازبینیِ کد**.

قاعده: «جوازِ تجاری روی پرونده ⇒ شخصیتِ حقوقی، قطعی». منطقی به‌نظر می‌رسد —
یک شخصِ حقیقی جوازِ تجاری ندارد. ولی **بانک هنگام افتتاحِ حسابِ حقیقی، جوازِ
محلِ کارِ مشتری را به‌عنوانِ مدرکِ اشتغال و اقامت می‌گیرد.** پس جوازِ روی یک
پروندهٔ شخصی می‌تواند مالِ کارفرما باشد.

سه درس:

1. **«فقط X این را دارد» را از کسی بپرس که فرآیند را می‌داند.** استدلالِ منطقیِ
   من بی‌عیب بود؛ چیزی که نمی‌دانستم **رویّهٔ افتتاحِ حساب** بود. دانشِ دامنه با
   استدلال جایگزین نمی‌شود.
2. **شاهد را «مؤیّد» بگذار، نه «دلیل».** حالا جواز فقط وقتی قطعی می‌شود که چیزِ
   دیگری هم بگوید شرکت است؛ به‌تنهایی «کم» است و طبقِ قاعده هرگز یک مقدارِ
   ذخیره‌شده را متهم نمی‌کند. شاهدِ ضعیف حذف نشد — **رتبه‌اش** درست شد.
3. **پیش از افزودنِ قاعدهٔ جایگزین، روی دادهٔ واقعی اندازه بگیر.** می‌خواستم
   «دو نام با `&` ⇒ حسابِ مشترک» را اضافه کنم؛ اندازه‌گیری روی دفتر نشان داد از
   ۱۳۲ موردِ دارای `&`، تقریباً همه شرکت‌اند («JAWAD ALUMINIUM & GLASS WORKS»).
   یک خطاسازِ تازه، درست پیش از نوشته‌شدن، کشته شد.

و یک نکتهٔ عملیاتی: **هر نوشتنی روی دادهٔ مشتری باید ردِ حسابرسی داشته باشد.**
وقتی می‌خواستم بدانم کدام رکوردها تغییر کرده‌اند، endpointِ اعمال هیچ لاگی
نگذاشته بود؛ فقط `updated_at` نجاتم داد. حالا لاگ هم می‌گذارد.

## Update 2026-09-28 (v145) — همان خطا، در آینه

درسِ v143 («جواز دلیل نیست») **کامل اجرا نشده بود**. قاعدهٔ قرینه‌اش دست‌نخورده
ماند و بیشتر آسیب می‌زد:

```python
if has_id and not corp:                     # ❌
    retail.append("پاسپورت/اماراتی‌آیدی دارد و هیچ نشانهٔ شرکتی ندارد")
```

روی پروندهٔ واقعی: **۶۴** ناسازگاریِ غلط (در برابرِ ۵ موردِ جواز). `ATLAS
MEDICAL FZCO`، `AL AZHAR MONEY EXCHANGE`، `GOLD STANDARD DMCC`، `AL ADAB
IRANIAN PRIVATE SCHOOL` — همه درست `corporate` ثبت شده بودند و به‌خاطرِ
پاسپورتِ **مدیرشان** «حقیقی» اعلام شدند.

### دو درسِ متمایز

**۱) مدرکِ هویتی ثابت می‌کند کسی شناسایی شد، نه اینکه حساب مالِ کیست.**
در افتتاحِ حسابِ شرکتی هم پاسپورت و اماراتی‌آیدیِ مدیر/صاحبِ امضا گرفته
می‌شود — خودِ فرمِ شرکتی این فیلدها را دارد. تعمیمِ حرفِ مالک: **هیچ سندی که
از هر دو نوعِ مشتری گرفته می‌شود، نوعِ مشتری را تعیین نمی‌کند.** قاعدهٔ عملی:
پیش از اینکه یک مدرک را «قطعی» بشماری، بپرس *آیا این مدرک از نوعِ دیگر هم
گرفته می‌شود؟* اگر بله، مؤیّد است، نه دلیل.

**۲) شرطِ `not corp` به کاملی‌بودنِ الگو تکیه داشت — و الگو کامل نبود.**
`_CORP_RE` نامِ واقعیِ این دفتر را نمی‌شناخت: `FZCO`, `DMCC`, `GmbH`, `TRDG`,
`TR.`, `EXCHANGE`, `B.V.`, `SOLE PROPRIETORSHIP`, `SUPER MARKET`. پس
«هیچ نشانهٔ شرکتی ندارد» یعنی «الگوی من نشانه‌ای ندید» — نه «نشانه‌ای نیست».

> **یک نتیجه‌گیریِ منفی که بر پایهٔ یک الگوی دست‌نویس است، هم‌قدرِ آن الگوست.
> هرگز آن را به‌عنوانِ شاهدِ مثبتِ سمتِ مقابل استفاده نکن.**

این خطرناک‌ترین بخش بود، چون غیبتِ یک نشانه بی‌صدا به **حضورِ** نشانهٔ مقابل
ترجمه می‌شد.

### چه شد

* مدرکِ هویتی هم مثلِ جواز به **مؤیّد** تنزل یافت (`low` — و `disagrees`
  مقدارِ `low` را نادیده می‌گیرد). حذف نشد: همچنان به‌عنوان یادداشت گزارش می‌شود.
* `_CORP_TOKENS` از **دادهٔ واقعی** گسترش یافت (۴۷ از ۶۴ نامِ ناشناخته حالا
  شناسایی می‌شوند). فقط افزودن — هیچ توکنی تغییر نکرد یا حذف نشد.
* `TR` تنها **عمداً اضافه نشد**: با حرفِ اولِ نامِ اشخاص تصادم دارد، و اشتباهِ
  سمتِ «شرکتی» گران‌تر است (فرمِ دیگری باز می‌شود و KYC دیگری خواسته می‌شود).
* **سنجشِ مثبتِ کاذب پیش از تحویل:** روی ۱۵٬۰۰۰ حسابِ واقعیِ ثبت‌شده به‌عنوان
  `retail`، توکن‌های نو فقط **۲۶** مورد (۰٪ گِرد) را علامت زدند و هر ۲۶ واقعاً
  کسب‌وکارند (`... TRADING LLC`, `AL-ITIHAD DRIVING SCHOOL`). یعنی گسترش،
  سیلِ اتهام نساخت. **این سنجش پیش از کامیت انجام شد، نه بعدش.**

## Update 2026-09-28 (v147) — بارِ سوم، و این بار الگو را نوشتم

اولین اجرای روی **کلِ** پرونده (۴۴٬۶۰۸ حساب — پیش‌تر همیشه نمونه بود، v144) شش


### درسِ نو ۱ — یک عنوان فقط جایی که عنوان می‌نشیند معنا دارد

`\bmiss\b` در «NEW MISS PARIS» گیر می‌کرد. عنوانِ واقعی **اولِ** نام می‌آید
(«MR:A.K.UMMER»). لنگر انداختن به ابتدای رشته، استفادهٔ تجاریِ وسطِ نام را حذف
کرد و موردِ واقعی را نگه داشت.

> **قاعده:** برای هر الگویی که «نقش» را تشخیص می‌دهد (عنوان، پیشوند، واحد،
> شکلِ حقوقی) بپرس *این کلمه در آن نقش کجا می‌نشیند؟* و همان‌جا را ببند.
> `\b…\b` جای یک کلمه را نمی‌گوید، فقط وجودش را.

### درسِ نو ۲ — «نوعِ فعالیت» نوعِ مشتری نیست (و این بارِ سوم بود)

`business_type = "RETAIL SALE OF WARE AND TOOLS"` یعنی این مغازه **خرده‌فروشی
می‌کند** — که کارش است، نه هویتش. یک مغازه شرکت است.

این **دقیقاً** همان آزمونی است که v143 و v145 ساختند، و من در v145 ننوشتمش به
شکلی که خودکار اجرا شود. پس بگذار صریح باشد، به‌عنوانِ چک‌لیستِ اجباری برای هر
شاهدِ جدید:

> **پیش از اینکه هر مقداری را شاهدِ «نوعِ X» بشماری، بپرس:**
> ۱. آیا این مقدار برای نوعِ **دیگر** هم ثبت می‌شود؟ (جواز ⇒ بله؛ پاسپورت ⇒ بله؛
>    «RETAIL SALE» ⇒ بله) اگر بله، **مؤیّد است، نه دلیل**.
> ۲. آیا این کلمه در حوزهٔ واقعیِ ما نقشِ دیگری دارد؟ (SHEIKH، ENG، MISS، CO
>    به‌عنوانِ نامِ میانی) اگر بله، **جایش را محدود کن یا رهایش کن**.
> ۳. نتیجه‌گیریِ **منفی**‌ات («هیچ نشانهٔ شرکتی ندارد») به یک الگوی دست‌نویس تکیه
>    دارد؟ اگر بله، **هرگز شاهدِ مثبتِ سمتِ مقابل نشود**.

سه بار همین خطا در یک هفته، در سه شاهدِ مختلف. الگو را باید در **چک‌لیست** نوشت،
نه در یک تصحیحِ موردی؛ وگرنه بارِ چهارم هم می‌آید.
