# پیش‌فرضی که شبیهِ تصمیم است، رکورد را خراب می‌کند

## 🎯 چالش / Challenge

یک فیلدِ دسته‌بندی (مثلاً «حقیقی / حقوقی»، «فعال/غیرفعال»، «داخلی/خارجی») پیش‌فرضِ
«معقول» گرفت:

```python
account_type = Column(Enum(AccountType), default=AccountType.RETAIL)
```

و ایمپورتِ انبوه هم همان کار را کرد:

```python
a = str(rec.get("account_type") or "retail").lower()   # ستون نبود ⇒ retail
```

نتیجه این است که دیتابیس دیگر نمی‌تواند این دو را از هم تشخیص دهد:

| واقعیت | مقدارِ ذخیره‌شده |
|---|---|
| «این حساب شخصِ حقیقی است» (کسی تصمیم گرفت) | `retail` |
| «هیچ‌کس تعیین نکرده» (پیش‌فرض) | `retail` |

این یک خطای «داده‌ی غلط» نیست؛ **نابودیِ اطلاعات** است — آن‌هم بی‌صدا، در پهن‌ترین
مسیرِ ورودیِ سیستم. هیچ تستی قرمز نمی‌شود، هیچ لاگی چیزی نمی‌گوید، و ماه‌ها بعد
کاربر می‌گوید «چرا برای یک شرکت فرمِ شخصی باز می‌کند؟».

**نشانهٔ تشخیصیِ قطعی:** کدی که می‌گوید «اگر تعیین نشده بود، از کاربر بپرس»
تبدیل به **کدِ مرده** می‌شود — چون هرگز تعیین‌نشده وجود ندارد.

## 💡 راه‌حل / Solution

1. **«نمی‌دانم» یک مقدارِ درجه‌یک است، نه غیابِ مقدار.** یک عضوِ صریح
   (`UNKNOWN`) به enum اضافه کن و پیش‌فرض را همان بگذار.
2. **هر جایی که مقدار می‌سازد را پیدا کن، نه فقط مدل را.** ایمپورت‌ها،
   `or "default"`ها، و نگاشت‌های فرم. `grep` روی نامِ فیلد، نه روی نامِ مدل.
3. **دادهٔ موجود را بازنویسی نکن.** سیستم نمی‌داند کدام مقدارها تصمیمِ واقعی
   بوده‌اند؛ بازنویسی، حدسی دیگر روی حدسِ قبلی است.
4. **یک طبقه‌بندِ مبتنی بر شواهد بساز که فقط نظر می‌دهد.** از فیلدهایی که
   خودِ دیتابیس دارد، با **شواهدِ مثبت فقط**؛ نبودِ شاهد ⇒ `unknown`، نه حدس.
5. **دو مشکل را هرگز یکی نکن:** «تصمیم گرفته نشده» و «تصمیم با شواهد نمی‌خواند»
   دو یافتهٔ جدا با دو راه‌حلِ جدا هستند. یکی‌کردنشان عددِ واقعی را پنهان می‌کند.
6. **اصلاح، بازبینی‌محور:** فهرست + دلیل + دکمهٔ اعمالِ تک‌به‌تک. هیچ سوییچِ
   «همه را درست کن» روی heuristic.
7. **قاعدهٔ پایش اضافه کن**، وگرنه دفعهٔ بعد هم ساکت می‌ماند.

## 🧪 نمونه کد (Anonymized)

```python
class Kind(str, Enum):
    A = "a"; B = "b"
    UNKNOWN = "unknown"      # «هیچ‌کس تعیین نکرده» — یک وضعیتِ واقعی

kind = Column(Enum(Kind), default=Kind.UNKNOWN)      # نه Kind.A

def from_listing(rec) -> str:
    v = str(rec.get("kind") or "").strip().lower()
    return v if v in VALID else "unknown"             # نه "a"
```

طبقه‌بند — فقط نظر، با دلیل:

```python
@dataclass
class Verdict:
    guess: str = UNKNOWN
    confidence: str = "none"      # high | medium | low | none
    reasons: list = field(default_factory=list)
    counter_reasons: list = field(default_factory=list)

def classify(**evidence) -> Verdict:
    strong, weak = [], []
    if evidence["licence_no"]:  strong.append("جوازِ تجاری فقط برای شخصیتِ حقوقی صادر می‌شود")
    if evidence["partners"]:    strong.append("شریکِ ثبت‌شده دارد")
    # شواهدِ ضعیف فقط وقتی حرف می‌زنند که شاهدِ قوی نباشد
    if evidence["id_doc"] and not strong: weak.append("فقط مدرکِ هویتِ شخصی دارد")
    ...
    return Verdict(...)          # هیچ نوشتنی

def disagrees(stored, v: Verdict) -> bool:
    """تصمیمِ ذخیره‌شده با شاهدِ مطمئن جور نیست؟ «تعیین‌نشده» تناقض نیست."""
    if is_undecided(stored) or not v.decided or v.confidence in ("none", "low"):
        return False
    return family(stored) != family(v.guess)
```

## ⚠️ نکات حیاتی / Pitfalls

- **شاهدِ ضعیف را با شاهدِ قوی قاطی نکن.** پروندهٔ یک شرکت به‌درستی پاسپورتِ
  *مدیرش* را دارد — فرمِ شرکتی اصلاً فیلدِ «Manager Emirates ID» دارد. مدرکِ
  هویتی فقط **در نبودِ** هر شاهدِ شرکتی معنا دارد.
- **تطبیقِ کلمه، نه زیررشته.** `EST` داخلِ `Ernesto` و `CO` داخلِ `Cotton` در
  مقیاسِ چندهزار رکورد فاجعه می‌سازد. `\b…\b`.
- **مقدارِ زیرمجموعه تناقض نیست:** اگر `sme` زیرمجموعهٔ `corporate` است،
  «`sme` ذخیره شده ولی شواهد می‌گوید corporate» نباید یافته باشد.
- **گزارشِ سیل‌آسا خوانده نمی‌شود:** اگر ۴۰۰۰ رکورد ایراد دارند، ۲۵ نمونه +
  یک خطِ جمع‌بندی بده، نه ۴۰۰۰ یافته که بقیهٔ گزارش را دفن می‌کند.
- **تستی که پیش‌فرضِ غلط را تثبیت کرده بود را پیدا کن.** این‌جا دو تست دقیقاً
  `assert customer.account_type == RETAIL` داشتند؛ آن‌ها باگ را **قفل** کرده
  بودند. تست را به قراردادِ درست به‌روز کن و دلیلش را همان‌جا بنویس.

## 🔁 چطور در جای دیگر اعمال کنیم / How to Apply Elsewhere

برای هر فیلدِ دسته‌بندی/وضعیت این‌ها را بپرس:

1. اگر کسی تعیین نکند، چه ذخیره می‌شود؟ اگر یک مقدارِ **معتبرِ دامنه** است ⇒ باگ.
2. آیا می‌شود «تعیین‌نشده» را از «تعیین‌شده» تشخیص داد؟ اگر نه ⇒ باگ.
3. کدی هست که می‌گوید «اگر خالی بود بپرس»؟ آیا اصلاً اجرا می‌شود؟ اگر نه،
   همان‌جا ثابت می‌شود که پیش‌فرض اطلاعات را بلعیده.
4. چند مسیرِ دیگر همین مقدار را می‌سازند؟ (`or "x"` را grep کن.)
5. آیا دیتابیس شواهدی دارد که بشود با آن تصمیم را سنجید؟ اگر بله، گزارشش کن.
