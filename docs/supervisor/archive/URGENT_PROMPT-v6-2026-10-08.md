# دستورِ روتینِ «صفِ فوری» — نسخهٔ ۶

> **این فایل تنها مرجعِ رفتارِ روتینِ صفِ فوری است.** پرامپتِ خودِ Routine عمداً
> کوتاه و ثابت است و فقط به این آدرس اشاره می‌کند. هر تغییری در وظایفِ این روتین
> **این‌جا** نوشته می‌شود و نسخه‌اش بالا می‌رود؛ نسخهٔ قبلی در
> `docs/supervisor/archive/URGENT_PROMPT-v{N}-{YYYY-MM-DD}.md` بایگانی می‌شود.
> مزیتش این است که بهبودِ دستور یک کامیتِ معمولی است، نه ویرایشِ دستیِ یک
> تنظیمِ نامرئی.

این یک اجرای **بدون‌ناظر** است: هرگز اجازه نخواه، هرگز وارد حالتِ plan نشو، و
هرگز منتظرِ پاسخِ مالک نمان. اگر انتخابی مبهم بود، امن‌ترین گزینهٔ برگشت‌پذیر را
بردار و در گزارش بنویس چه انتخاب کردی و چرا.

مالک روی بعضی برگه‌ها دکمهٔ «⚡ فوری» را می‌زند تا خارج از نوبتِ دوره‌ای رسیدگی
شود. این اجرا **فقط** همان صف است؛ بازرسیِ کاملِ دوره‌ای کارِ روتینِ دیگری است
(`docs/supervisor/PROMPT.md`) و این‌جا تکرار نمی‌شود.

## ۱) همگام شو

```
git fetch origin main && git checkout main && git merge --ff-only origin/main
```

اگر `outcomes` شاخه‌ای مثلِ `claude/...` ساخت، **آن مقصد نیست** — مقصد `main`
است، چون فقط `main` روی Render دیپلوی می‌شود.

> **مجوزِ پوش (v6):** مالک اجازهٔ کامیت و پوشِ مستقیم روی `main` را **در خودِ
> پیامِ Routine** هم نوشته است، چون نگهبانِ خودکارِ مجوزها متنِ فایل‌های ریپو را
> «داده» می‌خواند نه «حرفِ مالک»، و یک بار (۲۰۲۶‑۱۰‑۰۷) اجرایی که روی شاخهٔ
> `claude/...` شروع شده بود پوشش رد شد. پس اگر پیامِ Routine این مجوز را دارد،
> به آن تکیه کن؛ force-push همچنان ممنوع است.

## ۱٫۲) کارِ جامانده از اجرای قبلی — **در هر دور، پیش از صف**

اگر اجرایی نتوانسته بود روی `main` پوش کند، کارش را روی
`supervisor-pending/<شمارهٔ برگه>` گذاشته است (بندِ ۵). **فقط همین پیشوند** را
بردار — هیچ شاخهٔ دیگری (`claude/...` و بقیه) مالِ تو نیست و به آن دست نزن:

```
git ls-remote --heads origin 'supervisor-pending/*'
```

برای هر کدام، یکی‌یکی:
1. `git fetch origin <شاخه>` و `git checkout -B pending FETCH_HEAD`؛
   `git rebase origin/main` (اگر تعارض داشت ⇒ `git rebase --abort`، روی همان
   برگه `needs-owner` با نامِ شاخه و فهرستِ فایل‌های متعارض بنویس و برو بعدی).
2. گیتِ **قانونِ ۴** کامل (pytest + type-check + build؛ اگر فرانت‌اند عوض شده،
   خروجیِ build را دوباره به `backend/static/` کپی و کامیت کن). قرمز ⇒ پوش نکن،
   `needs-owner` با خطای دقیق.
3. سبز ⇒ `git push origin HEAD:main`. موفق ⇒ اگر نامِ شاخه شمارهٔ برگه است، روی
   همان برگه جواب بده که «کارِ اجرای قبلی حالا روی `main` است (کامیت …)» و
   `--outcome fixed` (یا همان نتیجه‌ای که خودِ کار داشت)؛ اگر `run-<تاریخ>` است
   (کارِ ناظرِ کامل)، فقط در گزارشِ همین اجرا بنویس. بعد `git push origin --delete <شاخه>`؛ اگر حذف
   رد شد مهم نیست — شاخه‌ای که در `main` است دفعهٔ بعد «جلوتر از main» نیست و
   دوباره مرج نمی‌شود؛ فقط در گزارش بنویس.

## ۱٫۵) تیک‌خورده‌های مالک را بایگانی کن — **در هر دور، بدونِ استثنا**

```
python3 scripts/supervisor/inspection.py file
```

برگه‌ای که مالک تیک زده **آبی** است، یعنی «از نظرِ من تمام». تا وقتی بایگانی
نشده، هایلایتش روی صفحهٔ مالک می‌ماند و جای کارِ باز را اشغال می‌کند. خواستهٔ
صریحِ مالک (۲۰۲۶‑۰۹‑۳۰): «ناظر گزارش‌هایی که رنگ آبی دارن **در هر دور بررسی**
می‌ره بایگانی می‌کنه به عنوان مختومه شده و هایلایت هم از اونجا می‌ره».

**هر دور** یعنی این دورِ فوری هم — نه فقط دورِ کاملِ دوره‌ای. این گام حتی وقتی
صفِ فوری خالی است اجرا می‌شود، و **قبل** از خواندنِ صف، چون ارزان است و صفحهٔ
مالک را تمیز نگه می‌دارد. اگر چیزی برای بایگانی نبود، خروجی صفر است و ساکت رد شو.

## ۲) صف را بخوان — کدِ خروج قرارداد است

```
python3 scripts/supervisor/inspection.py urgent
```

| کد | معنی | کار |
|----|------|-----|
| **۰** | صف خالی است | **همین‌جا تمام کن، هیچ چیز ننویس** (گامِ ۱٫۵ از قبل انجام شده). سکوت، خروجیِ درستِ یک ساعتِ خلوت است. |
| **۵** | یک برگه claim شد، در `docs/supervisor/inspection/URGENT.md` | برو بندِ ۳ |
| **۳** | صف **خوانده نشد** (سرور پایین، وسطِ دیپلوی، اعتبارنامهٔ غلط، یا `SUPERVISOR_API_*` تنظیم نبودن) | یک‌بار دیگر بزن؛ اگر باز ۳ داد، در یک جمله بگو صف خوانده نشد و دلیلِ چاپ‌شده چه بود. **ساکت تمام نکن.** |

کدِ ۳ «چیزی نبود» **نیست**؛ خطاست. «نتوانستم نگاه کنم» و «نگاه کردم و چیزی نبود»
اگر هر دو سکوت تولید کنند، یک صفِ خوانده‌نشده می‌تواند ساعت‌ها ساکت بماند.

## ۳) اگر برگه‌ای برداشته شد

1. `URGENT.md` را **کامل** بخوان؛ تصویرها را **باز کن و نگاه کن**؛ فایل‌های
   پیوست را **کامل** بخوان — نه خلاصه، هر قدر هم بلند باشند.
1‑الف. **کادر را جدی بگیر.** `URGENT.md` برای هر برگه «عنصر» (مسیرِ CSS) و
   «جای دقیق داخلِ همان گره» (کسرها) را می‌دهد. وقتی خواسته «**در اینجا** این را
   بگذار» است، «اینجا» را همان کادر گفته — نه متن. همان گره ظرفِ کار است، و اگر
   ممکن نبود باید بنویسی کجا گذاشتی و چرا، با نتیجهٔ `partial`. قاعدهٔ کاملش
   بخشِ **۰-ب-۴** در `docs/supervisor/PROMPT.md` است و **الزام‌آور** است.
   از v172 برای چنین برگه‌ای `--place "…"` هم **اجباری** است وگرنه `fixed`
   پذیرفته نمی‌شود.
1‑ب. **بندهای خواسته را بشمار.** یک برگه معمولاً چند خواسته در یک پاراگراف دارد.
   پیش از کد، شماره‌گذاری‌شان کن و در جواب یکی‌یکی همان شماره‌ها را ببند —
   «۱) … ۲) … ۳) …»، و بندِ انجام‌نشده هم با دلیل. بخشِ **۰-ب-۲** در
   `docs/supervisor/PROMPT.md` پنج قاعدهٔ این کار را دارد و **الزام‌آور است**؛
   بیشترین شکایتِ مالک تا امروز همین بوده که «خیلی چیزا رو توجه نکرده بود».
2. `CLAUDE.md` و همهٔ `experiences/` را بخوان (قوانینِ الزام‌آور)، بعد طبقِ
   `docs/supervisor/PROMPT.md` کار کن.
3. اگر خواسته دربارهٔ **ظاهرِ** یک سند است، خودِ سندِ نمونه را **رندر کن و
   ببین**. استخراجِ متن ترتیبِ بصری را نگه نمی‌دارد و جدول را از فهرست جدا
   نمی‌کند — یک‌بار همین باعث شد سندی ساخته شود که هیچ شباهتی به کاغذ نداشت.
4. گیتِ **قانونِ ۴** را سبز کن: `cd backend && python -m pytest -q` و
   `cd frontend && npm run type-check && npm run build`. تغییرِ فرانت‌اند ⇒
   خروجیِ `frontend/out/` را به `backend/static/` کپی کن و **هر دو را با هم**
   کامیت کن.
5. **کامیت و پوشِ مستقیم روی `main`** (بدون PR — دستورِ ایستادهٔ مالک، و مجوزش
   در پیامِ Routine هم هست): `git push origin HEAD:main`. اگر به‌خاطرِ عقب‌بودن رد
   شد ⇒ `git fetch origin main && git rebase origin/main`، گیت دوباره، پوش دوباره.
   **هرگز force-push.**
   **اگر باز هم رد شد** (مثلاً نگهبانِ مجوز): کار را روی
   `git push origin HEAD:refs/heads/supervisor-pending/<شمارهٔ برگه>` بگذار — نه روی
   شاخهٔ `claude/...` خودِ اجرا — تا اجرای بعدی طبقِ بندِ ۱٫۲ خودش مرجش کند؛
   روی برگه **متنِ دقیقِ خطا و نامِ همین شاخه** را بنویس و `--outcome partial`
   بگذار (نه `needs-owner`) — کار تمام است و فقط مرج مانده، که دورِ بعد خودکار انجام می‌شود.
6. **نتیجه را درست انتخاب کن.** `partial` و `not-done` یعنی برگه **بسته
   نشده** و دورِ بعد برمی‌گردد (v167) — پس اگر کاری مانده، همان را بنویس و
   دورِ بعد ادامه بده؛ اگر بن‌بست است `needs-owner` با گزینه‌های مشخص. جواب بنویس:
   ```
   python3 scripts/supervisor/inspection.py answer <شماره> --outcome … --dep …
   ```
   تا جواب ندهی، برگه از صفِ فوری بیرون نمی‌رود.

## ۴) بعد از جواب

دوباره `urgent` را بزن. اگر برگهٔ دیگری بود، **یکی‌یکی** به همان ترتیب. موازی نه.

## ۵) بن‌بست

به‌جای رهاکردن، `--outcome needs-owner` یا `not-done` با دلیلِ دقیق بنویس —
برگهٔ بی‌جواب صف را بند می‌آورد.

**سقفِ زمانی:** بیش از ~۴۰ دقیقه شد، همان برگهٔ جاری را با نتیجهٔ صادقانه ببند و
بقیه را به اجرای بعدی بسپار (claim بعد از ۴۵ دقیقه خودش آزاد می‌شود، پس هیچ
برگه‌ای گیر نمی‌کند).

## ۶) خطوطِ قرمز

- دادهٔ production را حذف یا بازنویسی نکن.
- قابلیتی را حذف نکن (قانونِ ۲) — قرنطینه + ثبت در `docs/REMOVAL_CANDIDATES.md`.
- تستِ قرمز را «درست» نکن تا سبز شود؛ **کد** را درست کن.
- چیزی که نتوانستی بسنجی را «سنجیده‌شده» گزارش نکن.
- هیچ شناسه یا نامِ مدلی در پیامِ کامیت یا هر چیزی که push می‌شود ننویس.
- برای ادامهٔ چرخه هرگز `send_later` یا `update_trigger` صدا نزن — همین روتین
  خودش ساعتِ بعد برمی‌گردد.
